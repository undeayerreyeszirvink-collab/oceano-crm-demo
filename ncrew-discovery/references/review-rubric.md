# Review Rubric

Read this reference when you need a detailed review framework, scoring dimensions, default response structure, or common improvement patterns.

## What Good Output Looks Like

A strong review doesn't merely say "clear" or "unclear". It explains whether the material successfully turns a vague business request into a **stable, governable virtual employee definition** that can be handed to product, engineering, or process owners.

A useful review covers three layers:

| Layer | What to inspect | Strong quality | Weak quality |
|---|---|---|---|
| **Discovery quality** | Business context, trigger, actors, outputs, boundaries | Fast framing, selective questions, explicit risk boundary | Question dump, fragmented details, no stable scenario |
| **Design readiness** | Implementation flow | Clear role definition, scope, non-scope, permissions, human checkpoints | Generic assistant language, mixed responsibilities, unresolved approvals |
| **Demo/teaching quality** | Persuasiveness and reusability | Parallel comparison, explicit takeaways, reusable wording, visible artifact differences | Abstract explanation only, weak contrast, little reuse value |

## Review Dimensions

Use selectively — don't force all of them if not relevant.

| Dimension | Review question |
|---|---|
| **Framing** | Business whole established before drilling into specifics? |
| **Information hierarchy** | Questions and conclusions arranged in solution-shaping order? |
| **Role stability** | Stable virtual employee defined, or generic AI assistant? |
| **Boundary clarity** | Permission limits, approval gates, human takeover explicit? |
| **Artifact depth** | Stops at explanation, or shows handoff-grade outputs? |
| **Comparative clarity** | If comparison artifact: are low/high quality paths visibly different? |
| **Transferability** | Method shown as reusable across other enterprise scenarios? |
| **Training usability** | Could another operator reuse as a demo or workshop guide? |

## Default Response Structure

```
# [Artifact Name] Review

[One paragraph overall judgment: what the material does well and what type
of asset it currently is — strong explanation, persuasive demo, incomplete
handoff brief, etc.]

## Improvement 1
[Concrete weakness → recommended revision → why it matters]

## Improvement 2
[Concrete weakness → recommended revision → why it matters]

## Improvement 3
[Concrete weakness → recommended revision → why it matters]

## Priority Summary
[Small table ranking the three recommendations by likely impact]
```

## Phrasing Pattern

> The current document is already strong at **X**, but it still underperforms on **Y**. The next revision should add **Z**, because that would turn the artifact from **current state** into **better target state**.

## Reviewing Comparison Documents

When the artifact compares low-quality and high-quality discovery, pay special attention to:

| Focus | What to verify |
|---|---|
| **Symmetry** | Both sides at comparable depth — fair and sharp comparison? |
| **Outcome visibility** | Different end artifacts shown, not just different conversations? |
| **Evaluation standard** | Explains how to judge quality, not just asserts one side is better? |
| **Generalization** | Method portable beyond the single chosen scenario? |

## Common High-Value Improvements

These are often the most useful upgrades for comparison artifacts:

| Improvement | Why it works |
|---|---|
| Add complete low-quality brief vs high-quality brief comparison | Makes artifact-quality differences tangible |
| Add a scoring rubric | Makes the method teachable and reviewable |
| Add a second mini-case from another function | Proves generalization |
| Add a step-by-step workshop script | Turns the piece into a facilitation tool |
| Add failure patterns and anti-pattern labels | Helps users diagnose weak discovery faster |
| Add a vivid digital-employee profile for the high-quality version | Makes superior output easier to picture and remember |
