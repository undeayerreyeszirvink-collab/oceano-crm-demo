# AI应用价值评估模型 (AIVA) 评估框架

## 1. 模型概述

AIVA (AI Value Assessment) 是一套系统化的AI应用价值评估方法论，用于帮助企业在众多AI应用场景中做出优先级决策。模型采用**三层结构 + AI趋势修正**的设计：

```
┌─────────────────────────────────────────────┐
│           AI应用价值评估模型 (AIVA)            │
├─────────────┬───────────────┬───────────────┤
│  价值层      │  就绪度层      │  风险层        │
│  (能赚多少)  │  (能不能做)    │  (会不会翻车)   │
├─────────────┼───────────────┼───────────────┤
│ • 效率提升   │ • 数据成熟度   │ • 技术复杂度   │
│ • 成本节省   │ • 技术基础     │ • 变革阻力     │
│ • 收入增长   │ • 组织能力     │ • 数据隐私     │
│ • 体验改善   │ • 流程标准化   │ • 供应商依赖   │
└─────────────┴───────────────┴───────────────┘
              ↓ 叠加 AI 趋势修正 ↓
┌─────────────────────────────────────────────┐
│           AI趋势修正因子                      │
│ • 能力边界变化（LLM/Agent/多模态）             │
│ • 成本结构变化（推理成本下降）                  │
│ • 实施模式变化（API/Agent/低代码）             │
└─────────────────────────────────────────────┘
```

### 设计理念

- **价值层**回答"值不值得做"——量化AI能带来的业务收益
- **就绪度层**回答"能不能做"——评估组织当前的实施条件
- **风险层**回答"会不会翻车"——识别实施过程中的潜在障碍
- **AI趋势修正**叠加技术演进的影响——AI领域快速发展，静态评估容易过时

三层结构确保评估的完整性：高价值但高风险的场景不会盲目推进，低风险但低价值的场景也不会浪费资源。

## 2. 12维度定义

### 2.1 价值层（权重40%）

价值层衡量AI应用能为企业带来的业务收益，从四个互补维度进行评估。

#### 2.1.1 效率提升

| 项目 | 内容 |
|------|------|
| **定义** | AI应用对业务流程处理速度和吞吐量的提升程度 |
| **关键评估点** | - 流程处理时间缩短比例<br>- 单位时间吞吐量增加幅度<br>- 人工操作步骤减少数量<br>- 端到端响应时间改善 |
| **典型数据来源** | - 现有流程耗时记录（工单系统、ERP日志）<br>- 员工工时统计<br>- 同业AI应用效率提升案例<br>- POC/试点项目实测数据 |
| **评分参考** | 1分=提升<10%；2分=10-25%；3分=25-50%；4分=50-75%；5分=>75% |

#### 2.1.2 成本节省

| 项目 | 内容 |
|------|------|
| **定义** | AI应用在人力成本、运营成本和错误成本方面的节省 |
| **关键评估点** | - 可替代/辅助的人力工时（FTE减少）<br>- 错误率下降带来的返工成本节省<br>- 运营资源消耗降低<br>- 合规违规罚款风险减少 |
| **典型数据来源** | - 部门人力成本预算<br>- 历史错误/返工成本统计<br>- 运营费用明细<br>- 合规罚款记录 |
| **评分参考** | 1分=年节省<50万；2分=50-200万；3分=200-500万；4分=500-1000万；5分=>1000万（根据企业规模调整基线） |

#### 2.1.3 收入增长

| 项目 | 内容 |
|------|------|
| **定义** | AI赋能带来的新增收入或现有收入提升 |
| **关键评估点** | - AI驱动的新产品/服务收入<br>- 转化率提升带来的增量收入<br>- 客户生命周期价值(LTV)增加<br>- 市场份额扩大潜力 |
| **典型数据来源** | - 营收数据与转化漏斗<br>- 客户价值分析报告<br>- 竞品AI应用收入影响案例<br>- 市场调研与客户访谈 |
| **评分参考** | 1分=收入影响<1%；2分=1-3%；3分=3-5%；4分=5-10%；5分=>10% |

#### 2.1.4 体验改善

| 项目 | 内容 |
|------|------|
| **定义** | AI应用对客户体验和内部用户满意度的提升 |
| **关键评估点** | - 客户满意度(CSAT/NPS)预期提升<br>- 服务响应速度改善<br>- 个性化程度提高<br>- 员工工作体验改善（减少重复劳动） |
| **典型数据来源** | - 现有CSAT/NPS评分<br>- 客户投诉数据<br>- 员工满意度调查<br>- 用户旅程分析 |
| **评分参考** | 1分=体验无明显变化；2分=局部改善；3分=关键环节显著改善；4分=端到端体验提升；5分=行业领先体验 |

### 2.2 就绪度层（权重30%）

就绪度层评估组织当前实施AI应用的条件成熟度。

#### 2.2.1 数据成熟度

| 项目 | 内容 |
|------|------|
| **定义** | 支撑AI应用所需数据的质量、可获取性和完备程度 |
| **关键评估点** | - 数据质量（完整性、准确性、一致性）<br>- 数据可获取性（有无API/数据管道）<br>- 数据量是否满足模型训练/微调需求<br>- 数据标注状态（已标注/未标注/可自动标注） |
| **典型数据来源** | - 数据资产盘点报告<br>- 数据质量检测结果<br>- 数据仓库/湖的元数据统计<br>- IT部门的数据治理评估 |
| **评分参考** | 1分=数据缺失或质量极差；2分=数据存在但质量不稳定；3分=核心数据可用，质量尚可；4分=数据完备且质量良好；5分=数据资产成熟，已有治理体系 |

#### 2.2.2 技术基础

| 项目 | 内容 |
|------|------|
| **定义** | 现有IT基础设施对AI应用的支撑能力 |
| **关键评估点** | - 计算资源（GPU/云服务/算力预算）<br>- API开放程度（系统集成能力）<br>- 现有技术栈与AI技术的兼容性<br>- DevOps/MLOps成熟度 |
| **典型数据来源** | - IT架构文档<br>- 云服务订阅与资源使用报告<br>- 系统集成现状评估<br>- 技术债务评估报告 |
| **评分参考** | 1分=无云/API基础；2分=有基础云服务，API少量开放；3分=主流云平台+核心系统有API；4分=完善的云原生架构+API优先设计；5分=已有MLOps流水线，AI就绪 |

#### 2.2.3 组织能力

| 项目 | 内容 |
|------|------|
| **定义** | 组织在AI人才、项目管理和变革管理方面的能力 |
| **关键评估点** | - AI/ML人才储备（内部或可调配外部资源）<br>- 项目管理能力（敏捷实施经验）<br>- 管理层AI认知与支持力度<br>- 跨部门协作机制 |
| **典型数据来源** | - 组织架构与人才盘点<br>- 历史AI/数字化项目执行记录<br>- 管理层访谈<br>- 培训和能力建设投入 |
| **评分参考** | 1分=无AI人才，管理层无认知；2分=少量外部合作经验；3分=有数据/AI团队，管理层支持；4分=成熟AI团队+敏捷实施经验；5分=AI中心化组织，文化成熟 |

#### 2.2.4 流程标准化

| 项目 | 内容 |
|------|------|
| **定义** | 目标业务流程的规范化和可重复程度 |
| **关键评估点** | - 流程是否有标准化文档（SOP）<br>- 流程执行的一致性（不同人/团队执行结果差异）<br>- 异常处理规则是否明确<br>- 流程变更的频率和可控性 |
| **典型数据来源** | - 现有SOP文档<br>- 流程审计报告<br>- 执行偏差统计<br>- 业务部门访谈 |
| **评分参考** | 1分=无文档，执行完全靠个人经验；2分=有部分文档，执行不一致；3分=核心步骤有SOP，基本规范；4分=全流程SOP+执行监控；5分=流程高度标准化，已有自动化基础 |

### 2.3 风险层（权重30%，反向计分）

风险层识别实施过程中的潜在障碍。**采用反向计分：风险越低，得分越高。**

#### 2.3.1 技术复杂度（反向计分）

| 项目 | 内容 |
|------|------|
| **定义** | AI应用实施的技术难度和集成复杂度 |
| **关键评估点** | - 所需AI技术的成熟度（已验证 vs 前沿实验）<br>- 系统集成复杂度（对接系统数量和难度）<br>- 定制开发工作量<br>- 性能/可靠性要求 |
| **典型数据来源** | - 技术方案评审<br>- 同类项目实施复杂度参考<br>- 供应商技术评估<br>- PoC验证结果 |
| **评分参考（反向）** | 5分=成熟方案，开箱即用；4分=轻度定制，有成功案例；3分=中度定制，技术可控；2分=高度定制，技术风险大；1分=前沿技术，无成熟方案 |

#### 2.3.2 变革阻力（反向计分）

| 项目 | 内容 |
|------|------|
| **定义** | 组织和人员对AI应用引入的抵触和适应成本 |
| **关键评估点** | - 受影响岗位的变化程度（职责重组/裁减）<br>- 用户学习曲线和培训需求<br>- 业务部门配合意愿<br>- 工会/员工关系风险 |
| **典型数据来源** | - 变革影响评估<br>- 利益相关者分析<br>- 员工调研<br>- 历史变革项目经验 |
| **评分参考（反向）** | 5分=流程辅助，用户欢迎；4分=低影响，培训即可；3分=部分岗位调整，需变革管理；2分=大范围岗位变化，阻力明显；1分=核心岗位替代，强烈抵触 |

#### 2.3.3 数据隐私（反向计分）

| 项目 | 内容 |
|------|------|
| **定义** | AI应用涉及的数据隐私合规风险和监管要求 |
| **关键评估点** | - 涉及的数据类型（个人信息/敏感数据/商业机密）<br>- 适用的监管法规（GDPR/个人信息保护法/行业法规）<br>- 数据跨境传输需求<br>- AI模型输入/输出中的隐私风险 |
| **典型数据来源** | - 数据分类分级报告<br>- 合规要求清单<br>- 法务/合规部门评估<br>- 行业监管动态 |
| **评分参考（反向）** | 5分=仅涉及公开/脱敏数据；4分=涉及一般个人信息，合规路径清晰；3分=涉及敏感数据，需专项合规措施；2分=涉及高敏感数据+跨境传输；1分=强监管行业+高敏感数据+无合规先例 |

#### 2.3.4 供应商依赖（反向计分）

| 项目 | 内容 |
|------|------|
| **定义** | AI解决方案对特定供应商的依赖程度和锁定风险 |
| **关键评估点** | - 核心能力是否依赖单一供应商<br>- 数据/模型的可迁移性<br>- 合同条款的灵活性（退出成本）<br>- 替代方案的可获得性 |
| **典型数据来源** | - 供应商评估报告<br>- 合同条款分析<br>- 技术方案的开放性评审<br>- 市场替代方案调研 |
| **评分参考（反向）** | 5分=开源方案/多供应商可选；4分=主流平台+标准接口，迁移成本低；3分=有一定依赖但可替换；2分=核心依赖单一供应商，迁移成本高；1分=深度锁定，无法替换 |

## 3. 评分公式

### 3.1 基本评分规则

每个维度采用 **1-5分** 制：

| 分值 | 含义 |
|------|------|
| 1 | 极低/极差 |
| 2 | 较低/较差 |
| 3 | 中等/一般 |
| 4 | 较高/良好 |
| 5 | 极高/优秀 |

### 3.2 层级得分计算

```
价值得分 = Σ(维度分 × 维度权重) / Σ维度权重
就绪度得分 = Σ(维度分 × 维度权重) / Σ维度权重
风险得分 = Σ(维度分 × 维度权重) / Σ维度权重
```

其中，每层的4个维度各有独立权重（详见第4节）。

### 3.3 综合得分计算

```
最终得分 = 价值得分 × 0.4 + 就绪度得分 × 0.3 + 风险得分 × 0.3 + AI趋势修正
```

- **价值层权重 = 40%**：业务价值是决策的首要驱动力
- **就绪度层权重 = 30%**：实施条件决定项目能否落地
- **风险层权重 = 30%**：风险控制避免投资损失
- **AI趋势修正 = -1.0 到 +1.0**：反映技术演进对评估结论的影响

### 3.4 得分范围

- 各层级得分范围：1.0 - 5.0
- 综合得分范围（未修正）：1.0 - 5.0
- 综合得分范围（含修正）：0.0 - 6.0（极端情况）
- 实际常见范围：1.5 - 5.0

## 4. 维度内权重

### 4.1 默认权重

每层的4个维度**默认采用等权（各25%）**：

| 层级 | 维度 | 默认权重 |
|------|------|----------|
| 价值层 | 效率提升 | 25% |
| 价值层 | 成本节省 | 25% |
| 价值层 | 收入增长 | 25% |
| 价值层 | 体验改善 | 25% |
| 就绪度层 | 数据成熟度 | 25% |
| 就绪度层 | 技术基础 | 25% |
| 就绪度层 | 组织能力 | 25% |
| 就绪度层 | 流程标准化 | 25% |
| 风险层 | 技术复杂度 | 25% |
| 风险层 | 变革阻力 | 25% |
| 风险层 | 数据隐私 | 25% |
| 风险层 | 供应商依赖 | 25% |

### 4.2 动态权重调整规则

根据用户陈述的优先级和业务特征，维度权重可以动态调整。调整遵循以下规则：

**规则一：同层内权重总和恒为100%**

任何调整后，同一层级内的4个维度权重之和必须等于100%。

**规则二：调整幅度限制**

- 单个维度权重范围：10% - 50%
- 单次调整幅度：不超过 ±15%

**规则三：触发条件与调整建议**

| 用户优先级/场景 | 调整维度 | 调整方向 | 建议权重 |
|----------------|---------|---------|---------|
| "降本增效是首要目标" | 成本节省 | ↑ | 35-40% |
| "想用AI开拓新业务" | 收入增长 | ↑ | 35-40% |
| "客户体验是第一优先级" | 体验改善 | ↑ | 35-40% |
| "数据基础薄弱" | 数据成熟度 | ↑ | 35-40% |
| "强监管行业（金融/医疗）" | 数据隐私 | ↑ | 35-40% |
| "组织刚接触AI" | 组织能力 | ↑ | 30-35% |
| "需要快速落地" | 技术复杂度 | ↑ | 30-35% |
| "担心团队接受度" | 变革阻力 | ↑ | 30-35% |

**规则四：调整须透明告知**

每次权重调整必须在评估报告中说明调整理由，确保评估过程可追溯。

## 5. AI趋势修正因子

AI趋势修正因子反映技术快速演进对评估结论的影响。修正值范围为 **-1.0 到 +1.0**，叠加到综合得分上。修正分为三类：

### 5.1 能力边界修正

AI技术能力的扩展改变了场景的可行性和价值判断。

| 场景特征 | 修正方向 | 幅度 | 原因 |
|---------|---------|------|------|
| 非结构化文本处理（合同审查、邮件分类、文档摘要） | 技术复杂度↓ | -0.5 ~ -1.0 | LLM已具备成熟能力，不再需要定制NLP模型 |
| 多步骤流程自动化（审批、调度、工单流转） | 可行性↑ | +0.5 | AI Agent具备工具调用和流程编排能力 |
| 多模态理解（图文混合文档、视频内容分析） | 技术复杂度↓ | -0.3 ~ -0.5 | 多模态大模型使图文混合处理难度大幅降低 |
| 创意内容生成（营销文案、产品描述、设计稿） | 价值↑ | +0.3 ~ +0.5 | 生成式AI使内容创作从高成本变为低成本高产出 |

**触发条件：** 当评估场景涉及上述特征时，自动应用对应修正。

### 5.2 成本结构修正

AI推理成本和模型部署成本的变化影响ROI计算。

| 场景特征 | 修正方向 | 幅度 | 原因 |
|---------|---------|------|------|
| API调用密集型场景（推理成本下降>50%） | ROI↑ | +0.5 ~ +1.0 | 模型推理成本持续下降，高频调用场景的经济性大幅改善 |
| 开源模型可满足需求（Llama/Qwen/DeepSeek等） | 供应商依赖↓（分数↑） | +0.3 ~ +0.5 | 开源模型消除了对商业API的单一依赖 |

**触发条件：**
- 推理成本修正：场景需要高频API调用（>1000次/天），且当前成本评估基于6个月前的定价
- 开源模型修正：评估的技术需求可被当前主流开源模型满足

### 5.3 实施模式修正

AI应用的交付方式变化影响实施门槛和周期。

| 场景特征 | 修正方向 | 幅度 | 原因 |
|---------|---------|------|------|
| 有成熟SaaS/API产品可用 | 技术复杂度↓ + 实施成本↓ | -0.5 ~ -1.0 | 无需从零开发，直接集成成熟产品 |
| 低代码/无代码AI平台可用 | 组织能力要求↓（分数↑） | +0.3 | 降低了对专业AI人才的依赖 |

**触发条件：**
- SaaS/API修正：目标场景在市场上存在3个以上成熟商业产品
- 低代码修正：目标场景可通过低代码AI平台（如Dify、Coze、百度千帆等）实现核心功能

### 5.4 修正叠加规则

- 多个修正因子可以叠加，但总修正值限制在 **-1.0 到 +1.0** 范围内
- 同方向修正叠加时取最大值+其余值×0.5（避免过度修正）
- 修正因子必须在报告中逐项列出并说明理由

**叠加公式示例：**
```
若有两个正向修正 +0.5 和 +0.3：
  总修正 = max(0.5, 0.3) + min(0.5, 0.3) × 0.5
         = 0.5 + 0.15 = 0.65

若有正向 +0.5 和负向 -0.3：
  总修正 = 0.5 + (-0.3) = 0.2（正负直接相加）
```

## 6. 评级标准

综合得分对应四个评级，每个评级有明确的含义、建议行动和参考时间线。

### 6.1 强烈建议实施（得分 >= 4.0）

```
评级：🟢 强烈建议实施
```

| 项目 | 内容 |
|------|------|
| **含义** | 场景价值高、组织就绪、风险可控。属于"必抓的果实"——不做就是在浪费机会。 |
| **建议下一步** | 立即立项，分配预算和团队资源。可直接进入方案设计和供应商选型阶段。建议设置3个月内启动的里程碑。 |
| **典型时间线** | 1-2周完成方案确认 → 1-2个月完成PoC/MVP → 3-6个月全面上线 |
| **关注要点** | 虽然整体评分高，仍需关注风险层中得分最低的维度，制定针对性缓解措施。 |

### 6.2 建议试点验证（得分 3.0 - 3.9）

```
评级：🟡 建议试点验证
```

| 项目 | 内容 |
|------|------|
| **含义** | 场景有价值，但某些条件尚不完备或存在可管理的风险。需要通过试点验证假设后再决定全面推广。 |
| **建议下一步** | 选择一个可控范围（单部门/单流程/单地区）启动试点项目。明确试点的成功标准和评估指标。 |
| **典型时间线** | 2-4周完成试点方案 → 2-3个月完成试点 → 1个月评估试点结果 → 决策是否全面推广 |
| **关注要点** | 重点关注得分<3.0的维度，试点期间验证这些薄弱环节是否可以改善。定义明确的Go/No-Go标准。 |

### 6.3 需要条件准备（得分 2.0 - 2.9）

```
评级：🟠 需要条件准备后再评估
```

| 项目 | 内容 |
|------|------|
| **含义** | 场景可能有价值，但当前就绪度不足或风险过高。需要先投入资源改善基础条件，再重新评估。 |
| **建议下一步** | 识别得分最低的2-3个维度，制定6-12个月的改善计划。例如：数据治理项目、团队能力建设、流程标准化等。 |
| **典型时间线** | 1个月完成改善计划 → 6-12个月执行改善 → 重新评估 → 视评分决定下一步 |
| **关注要点** | 不要急于上马AI项目。改善基础条件本身就是有价值的投资，对未来所有AI场景都有帮助。 |

### 6.4 当前不建议投入（得分 < 2.0）

```
评级：🔴 当前不建议投入
```

| 项目 | 内容 |
|------|------|
| **含义** | 场景价值不清晰、条件严重不足或风险过高。当前投入大概率无法获得正向回报。 |
| **建议下一步** | 暂缓该场景，将资源投入到评分更高的场景。保持关注——技术进步或组织变化可能在未来改变评分。建议12个月后重新评估。 |
| **典型时间线** | 当前无需行动 → 12个月后重新评估 → 根据新评分决定 |
| **关注要点** | 分析得分低的根因：是价值不足、条件不够、还是风险太高？不同根因对应不同的改善方向。如果是价值层得分低，可能该场景本身不适合用AI解决。 |
