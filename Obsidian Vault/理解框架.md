## 一、试点设计原则（先定边界）

1. **高痛点优先**：先选“问题最严重”的场景，容易出效果
2. **可控规模**：10–15人/1个大区，避免扩散失控
3. **链路完整**：必须覆盖“获客→跟进→报价→成交”
4. **利益绑定同步上线**：没有机制，技术必失败
	1. **只做3个功能**：语音报备 + 自动采集 + 提成锁定
## 、试点对象选择（建议组合）

### 🎯 区域：**华东工程 + 华北工程（双点对照）**

- **华东工程（主试点）**：复杂度高、成交额大、ROI明显
- **华北工程（对照点）**：冲突多、飞单/项目争抢更明显

### 👥 人员结构（共12–15人）

- 负责人（1人）：梁子豪（管理侧牵引）
- 核心销售（6–8人）：
    - 至少2个“高痛点”（如郑钱/毕晓东类型）
    - 至少1个“高效样本”（杨富华类型）
- 关键支持（3–4人）：
    - 运营/数据（1）
    - 财务/审批（1）
    - IT对接（1–2）

> 结构目的：**同时验证“最难用户”和“最好用户”是否都能用**

### 🚫 明确不纳入：

- 零售门店
- 全渠道BI
- 全量客户标签
- 历史数据清洗

> ==原则：**只做“新产生的数据流”**==


## 六、验收KPI（必须量化）

### 🎯 使用类（生死线）

- 周活跃率（WAU） ≥ **70%**
- 人均周报备 ≥ **5条语音**
- 48小时内有动作的商机占比 ≥ **80%**

### 🎯 数据类（真实性）

- 自动生成数据占比 ≥ **70%**
- 重复填报项下降 ≥ **50%**
- 客户唯一ID覆盖率 ≥ **90%（新增数据）**

### 🎯 业务类（结果）

- 有效跟进次数/人 ↑ **30%+**
- 报价→成交转化率 ↑ **5–10%（试点内）**
- 报表时间 ↓ **50%+**

**一、 给 AI 一个身份：数字员工工号**
我们不把 AI 当作一个工具，而是当作一名“数字员工”来管理 ：

唯一 ID： 每个智能体都有专属工号（DE-ID），绑定特定岗位和权责 。
权限隔离： AI 只能看到它被允许看到的业务数据（Ontology 切片），只能调用它被授权的技能（Skills） 。


**二、 给 AI 装上护栏：沙箱与安全网关**
确保 AI 的“手脚”在管控范围内，绝不越权操作：
封闭执行（沙箱）： AI 的代码在隔离的“沙箱”里运行，无法直接攻击公司核心系统 。
操作拦截（网关）： AI 所有的系统调用（如：下单、调价）必须经过 CLI Gateway 审核，验证权限、验证参数、过滤危险动作 。


**三、 给 AI 配上监军：审计与人工复核**
确保每一秒的操作都“看得见、管得住”：
全量审计： AI 的每一句话、每一个动作都永久关联工号并记录在案，不可篡改，随时复盘 。
关键审批（HITL）： 针对采购下单、生产参数修改等高风险动作，系统强制设定“人工确认”节点，人不动手，AI 动不了 。

“目前最大的问题不是没有数据，而是数据是被重复填报、人工加工之后才上来的，导致管理层无法看到真实业务。”
- **判定矩阵与决策树：** 提供了“复用范围、语义依赖、流程主权”三个维度的判定标准 。
    
- **简单易记的口诀：** “换行业还能用”是L1，“换企业还能用”是L2，“只有这家企业这样干”是L3

**语料护城河：** 实施过程中积累的“SOP拆解数据”和“人工审核后的纠偏记录 (HITL data)”是无价的 。这些真实业务场景中的“Bad Case”和修正方案，是通用的预训练模型无法提供的。


这种标准化流程（从Ontology提取到SOP拆解）保证了AI Agent能力的颗粒度适中，避免出现无法复用的“超级大Skill”

框架中定义了从非结构化的企业 SOP（标准作业程序）提取为标准化 Skills 资产的 9 个步骤 ：

1. **文档预处理**：将原始资料清洗、切分、分类，转为可解析文本块 。
    
2. **Ontology（本体）提取**：建立业务世界模型，抽取实体、角色、关系、状态、规则和事件 。
    
3. **SOP 拆解**：找出能力边界，拆分为步骤、判断、动作三类单元 。
    
4. **生成 Skill Candidate**：形成最小稳定复用单元，定义其输入、输出、步骤和依赖 。
    
5. **自动判层**：根据复用边界和依赖程度，将其划分为 L1、L2 或 L3 。
    
6. **补全依赖**：使 Skill 具备可编排性，绑定相关的 Ontology、其他 Skill、CLI 接口和 HITL（人工环路）依赖 。
    
7. **识别 HITL**：标出流程中的人工决策节点，例如审批、复核、补充信息、特批识别 。
    
8. **生成 SKILL.md**：输出可编辑的能力资产，生成标准技能草稿 。
    
9. **审核发布**：通过人工审核修正，防止边界漂移和越权，最终完成注册发布 。

**Skills 与 CLI 必须严格区分**：Skill 是业务能力的表达（即“为什么做、按什么规则做”），而 CLI 则是受控的执行接口（即“真正对系统执行什么动作”）

**Skill 其实是一个文件夹。里面可以放脚本、数据文件、参考代码、模板，甚至 [SQLite]数据库。Claude 能自己去翻这个文件夹，找到它需要的东西，然后用起来。**

SKILL:“建房子的需求说明书和原始图纸”**而框架需要的 SKILLS 是**“可以直接交给施工队（Agent 编排引擎）执行的标准化预制件”

这个问题问得很到位。我们来拆解一下。

当前设计的问题

MROCube 现在的做法是：

用户意图（模糊）
    ↓
单一 /api/v1/selection 端点
    ↓
内部 DAG 自己决定走哪条路
    ↓
返回结果


所有的路由判断都在黑盒里发生，调用方 Agent 完全不参与决策。

这带来的具体问题

1. 意图理解粒度太粗

pipeline 只有三档：fast_track / standard / exploratory

但真实工业采购场景的意图远比三档复杂：



|真实意图            |当前能对应吗？       |
|----------------|--------------|
|我有图纸，帮我找等效替代品   |勉强 exploratory|
|我只知道参数，不知道品牌    |standard      |
|我要跨平台比价，型号已知    |fast_track    |
|我要做一次性大批量采购，需要谈价|❌ 没有对应        |
|我的设备停线了，只要有货最快到 |❌ 没有对应        |

意图模糊，pipeline 选错，结果就会跑偏。

2. 调用方失去控制权

上层 Agent 无法干预内部 DAG 的执行。比如：

	∙	想跳过 ecosystem_scout（不需要替代品）→ 做不到
	∙	想让 fulfillment_officer 只查自有库存 → 做不到
	∙	想在 parametric_engine 之后插入人工审核 → 做不到

3. 错误定位困难

出了问题只能看到最终结果，不知道是哪个内部 Agent 出了问题，调试成本很高。

4. Token 浪费

每次调用都会完整跑一遍 DAG，即便用户只是想简单查个价格，也要走完全套流程。

你说的多 Skills 拆分，逻辑应该是这样

用户输入
    ↓
意图识别层（Intent Router）
    ↓
┌──────────────────────────────────────────┐
│  Skill A: 参数化精确匹配                  │  → 知道型号，找规格/库存
│  Skill B: 需求反推选型                   │  → 知道工况，不知道型号
│  Skill C: 替代品/等效品搜索              │  → 原型号停产/缺货
│  Skill D: 跨平台比价                     │  → 型号已定，只比价格
│  Skill E: 紧急采购（库存优先）            │  → 停线场景，速度第一
│  Skill F: 批量采购谈价                   │  → 大单，需要报价流程
└──────────────────────────────────────────┘
    ↓
各 Skill 返回结构化结果
    ↓
Aggregator（按需合并）


这样做的核心好处

1. 意图在外部显式化

不是黑盒内部猜，而是上层 Agent 明确知道”这个用户是 Skill C 场景”，可以做二次确认、可以记录、可以审计。

2. 每个 Skill 可以独立优化

比价 Skill 可以专门做缓存（价格数据变化慢），紧急采购 Skill 可以走更快的检索路径，互不干扰。

3. 组合调用成为可能

复杂场景可以串联：先走 Skill B（反推型号）→ 再走 Skill D（比价）→ 再走 Skill E（查库存）。这种编排在单一 endpoint 里根本做不到。

4. 可观测性大幅提升

每个 Skill 的调用、耗时、成功率都可以独立监控，出问题精确定位。

为什么他们没这样做？

可能的原因：

	∙	对外简化：单一 endpoint 对接入方更友好，降低集成门槛
	∙	内部已经是多 Agent：DAG 里已经有三个子 Agent，只是没对外暴露
	∙	商业考量：把能力细分暴露出来，等于把产品逻辑也暴露了

但这个取舍的代价就是：把控制权锁在自己这里，调用方 Agent 永远是被动的。

结论

你的判断是对的。单一 Skills 适合做简单工具封装，不适合做有深度意图差异的复杂选型场景。

真正 Agent-native 的设计，应该是把意图路由放在外部显式化，让 Skills 颗粒度更细、职责更单一，然后由上层 Orchestrator 决定怎么组合调用。这才是多 Agent 协作的精髓。​​​​​​​​​​​​​​​​



> “我们现在的 CRM 不是要让销售人员‘多干活’来满足管理，而是要用 AI 让销售‘少干活’来保住业绩。通过**零感知采集**，我们把销售的时间从 Excel 里抢回来还给市场；通过**利益绑定**，我们把公司的客户资产从业务员的脑子里抢回来放进系统。”
