# 欧神诺SKU查找工具 - 深度用户聚类分析

## 🎯 核心问题

10类用户要做成3-4个不同的流程，关键问题是：
1. **什么差异可以通过配置解决？**（不需要开发不同流程）
2. **什么差异必须分流？**（需要完全不同的前端应用）

---

## 深度分析：什么因素决定了必须分流？

### ❌ 容易导致代码分支爆炸和UX割裂的维度

#### 1. **搜索/查询方式** ⚠️⚠️⚠️ 最关键
```
不同的搜索方式 → 不同的组件 → 不同的过滤逻辑 → 代码分支爆炸

例子1：精确查询 vs 属性查询
  编码查询：输入框 + 搜索按钮 + 精确匹配
  属性查询：多选框 + 滑块 + 组合过滤 + 推荐排序
  → 搜索引擎配置完全不同
  → 前端组件无法复用
  → 如果混在一起，代码会充满 if-else

例子2：结构化查询 vs 情感化查询
  编码/规格查询：用户知道要什么
  房间类型查询：用户只知道应用场景
  → 推荐算法不同
  → 排序规则不同
  → 完全不同的UX
```

#### 2. **业务决策流程** ⚠️⚠️ 很重要
```
不同的决策流程 → 不同的用户心智 → 不同的信息流

例子：B2B采购 vs B2C购买
  B2B采购（工程方）：
    1. 确认需求 → 2. 查询库存 → 3. 验证质量 → 4. 洽谈价格 → 5. 签订合同
    
  B2C购买（消费者）：
    1. 浏览灵感 → 2. 选择产品 → 3. 查看评价 → 4. 申请样品 → 5. 购买
    
  → 用户关心的字段不同
  → 转化入口不同
  → 如果混在一起，用户会迷茫
```

#### 3. **权限隔离** ✓ 可以配置解决
```
权限隔离 可以 通过权限系统完全解决，不需要分流

例子：内部员工 vs 外部客户
  内部员工：
    • 可以看成本信息
    • 可以操作库存
    • 可以生成报表
    
  外部客户：
    • 看不到成本
    • 只能查看，不能操作
    • 不能导出原始数据
    
  解决方案：权限标记 + 字段权限控制
```

#### 4. **展示字段** ✓ 可以配置解决
```
不同用户关心不同字段，但可以通过【字段权限】解决

例子：供应链 vs 采购
  供应链：库存、交期、生产状态 最重要
  采购：成本、供应商、支付条件 最重要
  
  解决方案：
    • 对供应链显示：库存 > 交期 > 生产状态
    • 对采购显示：成本 > 供应商 > 支付条件
    • 通过字段权重和排序解决
```

#### 5. **国际化** ✓ 可以配置解决
```
多语言 和 多币种 可以通过i18n框架完全解决

例子：国内经销商 vs 海外经销商
  国内：中文、人民币、无特殊认证
  海外：英文/日文/韩文、美元/欧元、需要国际认证
  
  解决方案：i18n框架 + 货币配置
```

## 最优的聚类方案：3个流程（MVP）

### 聚类1️⃣：精确查询流（数据决策用户）

**包含用户**：
- 供应链经理 ✓
- 工程项目方 ✓
- 产品管理 ✓
- 质量/技术 ✓
- 采购/成本 ✓

**核心特征**：
```
输入方式  → 知道SKU编码，通过编码或规格精确查询
搜索方式  → 精确匹配、范围过滤、分类浏览
决策流程  → 收集数据 → 对比分析 → 做决策 → 执行操作
数据优先  → 库存、工艺、成本、交期是关键决策依据
权限      → 内部员工或特定外部客户（如大型工程方）
```

**前端流程**：
```
1. 搜索入口
   ├─ 编码输入框（自动补全）
   ├─ 规格下拉选择（长×宽×厚）
   └─ 快速搜索按钮

2. 过滤条件
   ├─ 颜色/花型
   ├─ 工艺方式（喷墨/布料/印花）
   ├─ 库存状态（现货/排产中）
   ├─ 库存数量范围
   └─ 交期范围

3. 结果列表（卡片展示）
   ├─ 产品编码/名称
   ├─ 规格/厚度/颜色
   ├─ 库存数量（各仓库）
   ├─ 交期承诺
   ├─ 生产厂家
   └─ 立即查看详情 按钮

4. 详情页
   ├─ 基本信息（编码、名称、规格）
   ├─ 库存分布（各仓库库存量）
   ├─ 技术参数（吸水率、厚度公差、执行标准）
   ├─ 工艺信息（坯体、光度、表面工艺）
   ├─ 历史数据（最近生产时间、库存趋势）
   ├─ 相关产品（相同规格的其他颜色）
   └─ 操作按钮
        ├─ 生成排产单（供应链）
        ├─ 生成采购单（工程方）
        ├─ 添加到对比（产品）
        ├─ 查看质量问题（质技）
        └─ 查看采购历史（采购）

5. 下一步动作
   ├─ 供应链 → 排产单生成 → ERP系统
   ├─ 工程方 → 采购单 → CRM系统
   ├─ 产品 → 库存分析 → BI系统
   ├─ 质技 → 工艺改进 → 质量系统
   └─ 采购 → 成本决策 → 财务系统
```

**用户内部差异处理**：

| 用户对 | 差异维度 | 处理方式 | 技术方案 |
|-------|--------|--------|--------|
| 供应链 vs 工程方 | 权限隔离 | 权限系统 | ①标记用户身份<br>②字段权限控制<br>③操作按钮条件显示 |
| 供应链 vs 工程方 | 数据展示 | 字段排序 | ①对供应链：库存优先<br>②对工程方：质保优先 |
| 供应链 vs 工程方 | 转化路径 | 工作流分支 | ①点击排产 → ERP<br>②点击采购 → CRM |
| 产品管理 vs 质技 vs 采购 | 分析维度 | 仪表板配置 | ①库存热度分析<br>②工艺质量分析<br>③成本趋势分析 |

**代码复用度**：
- 搜索和过滤组件：100% 复用
- 列表和卡片：95% 复用（只有部分字段不同）
- 详情页：90% 复用（字段显示不同，但结构相同）
- **总体代码复用度：85%+**
- 差异处理完全通过配置实现，无需代码分支

### 聚类2️⃣：视觉营销流（B2B销售用户）

**包含用户**：
- 国内经销商 ✓
- 海外经销商 ✓

**核心特征**：
```
输入方式  → 不知道SKU编码，通过风格/颜色/规格选择
搜索方式  → 属性多维组合过滤 + 推荐排序
决策流程  → 浏览产品 → 对比外观 → 申请样品 → 采购订单
视觉优先  → 产品图片和外观是第一决策因素
权限      → 外部B2B用户，注册用户
```

**前端流程**：
```
1. 搜索入口
   ├─ 风格选择（现代/仿古/工业等）
   ├─ 颜色选择（灰系/白系/棕系等）
   ├─ 规格范围（600×900 / 800×800等）
   └─ 搜索 按钮

2. 结果展示（网格布局）
   ├─ 高清产品卡片
   │  ├─ 大尺寸产品图（200×200px）
   │  ├─ 产品编码
   │  ├─ 产品名称/系列
   │  ├─ 规格和颜色
   │  ├─ 库存状态标签（现货/缺货）
   │  ├─ ★★★★ 评分
   │  └─ 查看详情 按钮
   └─ 排序选项（推荐/热销/新品）

3. 详情页
   ├─ 多图展示
   │  ├─ 正面图
   │  ├─ 侧面图
   │  ├─ 铺贴效果图
   │  └─ 3D预览（可选）
   ├─ 核心参数
   │  ├─ 规格、厚度、颜色
   │  ├─ 工艺方式
   │  ├─ 适用场景
   │  └─ 主要卖点
   ├─ 库存信息
   │  ├─ 库存充足度指示（图表）
   │  ├─ 预计交期
   │  └─ （不显示具体库存数字）
   ├─ 报价信息
   │  ├─ 参考价格区间
   │  ├─ 最小起订量（MOQ）
   │  └─ 获取报价 按钮
   ├─ 用户评价
   │  ├─ 平均评分
   │  ├─ 用户评论
   │  └─ 实际铺贴照片
   └─ 相关产品推荐

4. 转化页面
   ├─ 样品申请表单
   │  ├─ 数量、收货地址、需求说明
   │  └─ 提交按钮
   ├─ 加入采购单
   │  ├─ 保存到我的采购单
   │  └─ 提交询价
   └─ 分享功能
        └─ 复制链接、分享给客户

5. 下一步动作
   ├─ 样品申请 → 营销系统
   ├─ 采购询价 → CRM系统
   ├─ 分享推荐 → 营销记录
   └─ 评价反馈 → 内容系统
```

**用户内部差异处理**：

| 用户对 | 差异维度 | 处理方式 | 技术方案 |
|-------|--------|--------|--------|
| 国内 vs 海外 | 语言 | i18n框架 | ①中文 vs 英文/日文/韩文<br>②自动识别浏览器语言<br>③提供手动切换 |
| 国内 vs 海外 | 货币 | 货币配置 | ①RMB vs USD/EUR<br>②根据地区自动切换<br>③汇率实时更新 |
| 国内 vs 海外 | 认证标签 | 字段权限 | ①国内：无特殊认证<br>②海外：显示CE/ISO认证 |
| 国内 vs 海外 | 价格政策 | 后端配置 | ①不同地区的价格表<br>②不同的最小起订量 |

**代码复用度**：
- 搜索和过滤组件：100% 复用（i18n支持）
- 卡片和图片展示：100% 复用
- 详情页：95% 复用（国际化标签不同）
- 转化页面：90% 复用（表单字段可能不同）
- **总体代码复用度：90%+**
- 差异处理完全通过i18n和配置实现，无需代码分支

### 聚类3️⃣：独立消费流（B2C终端消费者）

**包含用户**：
- 终端消费者 ✓

**核心特征**：
```
输入方式  → 完全不同：房间类型、感受、风格
搜索方式  → 情感化、推荐式、场景化
决策流程  → 浏览灵感 → 选择产品 → 查看评价 → 申请样品 → 购买
体验优先  → 效果图、评价、本地可获性最重要
权限      → 公开访问，最少数据暴露
```

**前端流程**：
```
1. 首页和搜索入口
   ├─ 房间类型选择
   │  ├─ 卫生间、厨房、客厅、卧室、其他
   │  └─ 点击进入对应分类
   ├─ 风格选择（可选）
   │  ├─ 现代、古典、北欧、日式、新中式等
   │  └─ 与房间类型组合
   └─ 灵感浏览
        ├─ 编辑推荐
        ├─ 设计案例
        └─ 用户分享

2. 产品浏览页
   ├─ 效果图网格展示
   │  ├─ 大尺寸效果图（真实铺贴）
   │  ├─ 简化产品信息
   │  │  ├─ 产品名称
   │  │  ├─ 规格（简化：600×900）
   │  │  └─ 颜色描述（灰色系）
   │  ├─ 用户评分（★★★★★）
   │  └─ "查看详情" 按钮
   └─ 排序和筛选
        ├─ 新品优先、热销优先、好评优先
        └─ 颜色、规格 简化过滤

3. 产品详情页
   ├─ 沉浸式图片展示
   │  ├─ 铺贴效果图（多个场景）
   │  ├─ 产品特写
   │  ├─ 颜色对比
   │  └─ 3D预览（如果有）
   ├─ 用户这样说（评价展示）
   │  ├─ 用户评分分布
   │  ├─ 关键词标签（易清洁、防滑、耐脏）
   │  ├─ 用户评论
   │  └─ 用户上传照片
   ├─ 产品信息（简化）
   │  ├─ 产品名称和系列
   │  ├─ 规格和厚度（简化表示）
   │  ├─ 颜色和风格
   │  ├─ 适用场景（卫生间防滑、厨房易清洁等）
   │  ├─ 功能特点
   │  └─ 维护建议
   ├─ 相关产品推荐
   │  ├─ 同系列其他颜色
   │  ├─ 相似风格其他款
   │  └─ 搭配建议
   └─ 本地可获性
        ├─ 最近的展示店铺位置
        ├─ 店铺图片和点评
        └─ 导航和电话

4. 转化页面
   ├─ 申请免费样品
   │  ├─ 表单：姓名、电话、地址、房间类型
   │  └─ 提交申请
   ├─ 预约设计咨询
   │  ├─ 选择服务（免费设计咨询）
   │  ├─ 选择时间槽位
   │  └─ 确认预约
   └─ 在线购买
        ├─ 添加到购物车
        ├─ 跳转到京东/天猫等
        └─ 查询最近店铺

5. 下一步动作
   ├─ 样品申请 → 营销系统
   ├─ 设计咨询 → 预约系统
   ├─ 在线购买 → 电商平台
   └─ 用户评价 → 内容系统
```

**独立性说明**：
- 搜索方式：完全独立（房间vs编码，情感vs精确）
- 展示方式：完全独立（效果图vs参数表）
- 用户心智：完全独立（购买消费者 vs 采购决策者）
- **不应该与其他流程共享前端代码**

**与其他聚类的关系**：
- 前端流程：0% 代码复用（完全独立应用）
- 数据后端：100% 复用（相同的SKU数据库、库存、图片、评价）
- 架构建议：视为独立应用（可单独开发、部署、迭代）

可以完全并行开发，只需要API契约约定清楚。

## 常见问题解答

**Q: 为什么不把所有用户做成一个应用，用标签页切换？**

A: 因为搜索和过滤逻辑完全不同。一个应用里既要支持"编码查询"又要支持"房间类型选择"，会导致：
- 搜索组件充满if-else（维护nightmare）
- 用户界面割裂（有的页面显示编码输入，有的显示房间选择）
- 性能下降（加载不需要的功能）

**Q: 设计师工具为什么不单独开一个应用？**

A: 因为聚类分析显示，设计师既需要精确查询（聚类1）的能力，也需要视觉营销（聚类2）的展示。如果单独做，会导致：
- 搜索功能重复开发
- 卡片样式重复开发
- 需要维护三套相似的界面

**Q: 消费者应用为什么必须独立？**

A: 因为用户心智模型完全不同：
- B2B用户：我要查一个特定的产品
- 消费者：我想找灵感，不知道要什么

搜索和展示方式差异太大，无法在同一个应用里优雅处理。

**Q: 后端是不是也要分成3套？**

A: 完全不用。后端应该统一：
- 一个数据库（所有数据都在这里）
- 一个API层（提供通用搜索、聚合、工作流能力）
- 3个前端应用（通过API调用）

这样维护成本最低。

**Q: 权限系统很复杂吗？**

A: 不复杂。基于两个维度就够了：
1. **角色**：供应链、工程方、经销商、消费者等
2. **字段**：库存字段对消费者隐藏，成本字段对经销商隐藏

大多数权限管理框架都能轻松支持。

**Q: 如果用户想在应用间跳转怎么办？**

A: 大多数情况不需要。但如果需要：
- 在聚类1应用中，消费者相关的操作链接到聚类3应用
- 通过SSO实现统一登录
- 用户身份和权限自动传递

**Q: 国际化有多复杂？**

A: 不复杂。聚类2应用只需要：
- i18n框架（Vue-i18n 或 react-i18next）
- 文本翻译文件（JSON或YAML）
- 货币切换配置
- 日期/时间格式配置

这些都是标准做法，有很多开源库支持。
