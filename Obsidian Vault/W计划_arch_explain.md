## W计划智能家装平台 — 架构疑问回复

感谢您对架构方案的深入审视。这些问题非常专业且切中要害，下面逐一说明我们的思路和应对策略。

### 核心澄清：OpenClaw 是编排层，不是执行层

在回答具体问题之前，需要先澄清一个容易产生的误解：

**我们的架构并非"让 LLM 自主完成所有事情"，而是"让专业系统各司其职，由智能编排层灵活组合"。**

```
架构本质：

  用户需求
    ↓
  OpenClaw（智能编排层）—— 负责理解意图、拆解任务、调度流程
    ↓
  Skills（业务能力组合层）—— 将多个原子操作组合为业务动作
    ↓
  CLI（原子能力层）—— 封装各子系统的标准化接口
    ↓
  底层专业系统 ← 这里才是真正执行计算、存储、校验的地方
  （ERP / 算量引擎 / SKU数据库 / 设计工具 / 合作伙伴系统 ...）
```

LLM 在这个架构中的角色是**"理解意图"和"选择路径"**，而非"生成最终业务数据"。最终的报价数字、尺寸参数、SKU价格、BOM清单，全部来自底层确定性系统的输出。

### 一、关于确定性与容错率

**您的关切完全正确**——家装行业对数据精度零容忍，一个尺寸、一个价格都不能有误。

**我们的应对：LLM 只做"调度员"，不做"计算器"。**

以一个典型场景为例：

> 客户问：我家客厅铺某品牌瓷砖，大约需要多少钱？

OpenClaw 的编排过程如下：

| 步骤 | 调用的 Skill / CLI | 数据来源 | 输出性质 |
|------|-------------------|---------|---------|
| 1. 查询项目信息 | `project-cli.get` | 项目管理系统（确定性数据库） | 客厅面积 23.5m², 户型 L型 |
| 2. 查询 SKU 价格 | `sku-cli.search` + `pricing-cli.calculate` | SKU 数据库 + 价格规则引擎 | 单价 128元/m², 客户折扣 92折 |
| 3. 算量计算 | `measure-cli.calculate` | 第三方算量引擎（确定性算法） | 需要 27.8m²（含损耗率） |
| 4. 汇总报价 | `quote-cli.generate` | 规则引擎（确定性逻辑） | 总价 = 27.8 × 128 × 0.92 = **3,275元** |

可以看到：

- **每一步的数据都来自确定性系统**，不是 LLM 生成的
- LLM 的作用仅限于：理解"客户在问报价"→ 拆解为上述 4 步 → 按顺序调用
- 如果任何一步 Skill 调用失败或参数异常，**编排层会中断流程并上报人工处理**，而不是让 LLM "猜测"一个答案

**补充的工程保障措施：**

| 机制 | 说明 |
|------|------|
| **强类型参数校验** | 每个 CLI 命令的输入输出都有严格 Schema，不符合格式直接拒绝 |
| **规则引擎兜底** | 报价、折扣、BOM 等关键逻辑使用确定性规则引擎，不经过 LLM |
| **Human-in-the-loop** | 高金额报价提交、合同发起、生产排产确认等节点必须人工确认 |
| **幻觉防护** | LLM 产出的任何涉及数值/价格/尺寸的内容，必须经底层系统数据交叉验证后才展示 |
| **回退机制** | 工作流任意节点失败 → 回退到上一安全状态 → 通知人工介入 |

**一句话：LLM 负责"理解你要什么"，专业系统负责"算出精确结果"，两者各守其职。**

### 二、关于长周期状态管理

**您说得对**——家装项目长达数月，涉及多角色高频互动，不能依赖 LLM 的上下文记忆。

**我们的应对：项目状态以数据库为绝对真理，LLM 每次都从数据库读取最新状态。**

架构设计中，Project 是系统的**一等公民**，所有关键决策都结构化写入数据库：

```
每次交互的数据流：

  用户对话："把主卧地板换成实木的"
    ↓
  LLM 理解意图 → 识别为"修改设计方案中的材料选择"
    ↓
  调用 design-cli.update-material → 写入 Project 数据库
    ↓
  同时记录变更日志：
  {
    project_id: "P-2026-001",
    action: "material_change",
    room: "主卧",
    item: "地板",
    from: "强化复合",
    to: "实木",
    decided_by: "客户",
    timestamp: "2026-03-08T14:30:00"
  }
```

**关键设计原则：**

| 原则 | 具体做法 |
|------|---------|
| **数据库是唯一真相** | 每次 LLM 交互不依赖历史对话记忆，而是从 Project 数据库重新加载当前状态 |
| **决策结构化存储** | 客户的每个关键决策（材料变更、方案确认、报价同意）都以结构化数据写入，而非仅存在对话记录中 |
| **上下文按需注入** | LLM 每次被调用时，系统从数据库提取当前项目的关键状态摘要作为上下文，而非回溯全部历史对话 |
| **多角色共享状态** | 设计师、PM、客户看到的是同一份 Project 数据，不是各自的对话记忆 |

此外，我们前面提到的 **Shadow DB（补位数据层）** 正是为此设计——当开源子系统或合作伙伴系统无法存储某些过程数据时（如客户口头偏好、Excel维护的监理信息），Shadow DB 用扩展表在外围补齐这些字段，确保关键信息不会丢失在系统缝隙中。

**一句话：LLM 没有"记忆"负担——每一次对话都从数据库获取最新事实，不依赖上下文延续。**

### 三、关于算力成本与响应延迟

**您提到的成本和延迟问题是非常务实的考量。**

**我们的应对：分级策略——不同场景用不同的方案，不是所有事情都过大模型。**

| 场景类型 | 处理方式 | 响应时间 | 成本 |
|---------|---------|---------|------|
| **高频简单查询**（查价格、查进度、查状态） | 不经过 LLM，直接走 API 查数据库 | <0.5秒 | 极低 |
| **意图明确的操作**（预约、确认方案、提交报价） | 轻量模型做意图识别 → 直接调用对应 CLI | 1-2秒 | 低 |
| **需求沟通与咨询**（风格推荐、装修建议） | 中等模型（如 Claude Haiku 级别）对话 | 2-4秒 | 中等 |
| **复杂编排任务**（从需求到完整报价的多步编排） | 高级模型做规划 + 异步执行 | 异步通知 | 按需 |
| **重算力任务**（3D渲染、效果图生成） | 完全异步，后台排队处理 | 推送通知 | 独立计费 |

**具体优化手段：**

1. **模型分级部署**：项目不同阶段使用不同模型。早期获客咨询用轻量模型；进入方案报价阶段涉及精确数据时，LLM 仅做调度，计算由规则引擎完成
2. **热点数据缓存**：SKU 价格、门店信息、常见问答等高频数据做本地缓存，不需要每次都调用 LLM
3. **部分模型私有化部署**：对于高频调用的意图识别、文本摘要等标准化任务，使用私有化部署的小模型，降低成本并保证响应速度
4. **自研算法替代**：对于确定性逻辑（报价计算、SKU匹配、算量），使用自研算法或规则引擎，根本不走大模型
5. **异步交互设计**：对于重计算任务（3D效果图、完整方案生成），采用异步模式——用户提交需求后可继续其他操作，完成后通过微信/APP推送通知

**一句话：大模型只在"理解人话"时出场，大量日常操作走缓存、规则引擎和本地算法，重任务走异步。**

### 四、关于纯 CLI 交互的局限性

**完全同意**——家装是高度视觉化的行业，纯对话交互无法覆盖所有场景。

**我们的应对：CLI 在这里不是"命令行"，而是"对话能力层"；系统整体是 LUI + GUI 融合。**

需要澄清一个概念：我们架构中的"CLI"并非指用户看到命令行界面，而是指**底层能力的标准化封装接口**。用户实际接触到的是：

| 阶段 | 用户界面 | CLI 在底层做什么 |
|------|---------|---------------|
| **前期咨询** | 对话式交互（LUI） | 意图识别 → 调用 skill.lead_intake |
| **需求沟通** | 对话 + 案例图库浏览（LUI+GUI） | 提取需求标签 → 调用 skill.requirement_summary |
| **设计方案** | 可视化3D方案查看/标注（GUI为主） | design-cli 调用设计工具渲染结果 |
| **方案调整** | 拖拽/点选修改 + 语音/文字补充（GUI+LUI） | 用户点击换材料 → design-cli.update-material |
| **报价查看** | 表格+图表界面（GUI） | quote-cli 输出结构化数据，前端渲染 |
| **项目监控** | 时间线+照片墙（GUI） | project-cli.get-progress 返回进度数据 |

架构中涉及视觉化的子系统：

- **AI 生图 / 风格渲染**：作为独立 Skill 集成（可对接第三方AI生图服务或自建），编排层调用后结果展示在 GUI 中
- **3D 设计工具**：对接成熟的行业设计软件（如酷家乐、三维家等），通过 CLI 封装其能力
- **智能标注 / 批注**：用户在可视化界面上圈选区域 + 语音/文字说明 → 系统理解修改意图

**一句话：用户看到的是图形化界面，对话能力是锦上添花的辅助，CLI 是底层的技术封装层而非用户界面。**

### 五、关于 B 端供应链集成

**这确实是"深水区"，也是我们架构设计时重点考虑的问题。**

**我们的应对：用 CLI 标准化层屏蔽异构系统差异。**

现实中供应商的信息化程度参差不齐，我们的分层策略如下：

| 供应商类型 | 信息化水平 | 接入方式 | CLI 怎么做 |
|---------|---------|---------|----------|
| **大型合作伙伴** | 有完善 ERP/MES | API 对接 | CLI 封装其 API，标准化输入输出 |
| **中型供应商** | 有基础系统 | 数据同步 + API | CLI 做数据格式转换 + 适配 |
| **小型供应商** | 仅有 Excel | 提供标准化录入工具 | CLI 读取标准化数据表 |
| **施工团队** | 几乎无系统 | 提供专属小程序 | 小程序数据 → CLI → 平台 |

**关键设计：**

1. **CLI 层就是"标准化防火墙"**：无论背后是 SAP ERP 还是 Excel 表格，CLI 对上层暴露的接口格式完全一致。上层的 Skill 和编排引擎不需要知道底层数据源的差异
2. **渐进式接入**：Phase 1 先用 Shadow DB 补位表 + 人工录入覆盖不足；Phase 3 再逐步深度对接供应商系统
3. **供应商协同工具**：为信息化程度低的供应商提供标准化的协同小程序（订单确认、进度回报、库存更新），强制统一数据输入格式
4. **数据质量校验**：CLI 层内置数据格式校验和异常检测，不合格的数据不会进入业务流程

```
示例 - SKU 数据接入的标准化过程：

  供应商A（API）→ supplier-adapter-A → sku-cli.sync → 统一 SKU Schema
  供应商B（Excel）→ import-tool       → sku-cli.sync → 统一 SKU Schema
  供应商C（小程序）→ mini-app-form     → sku-cli.sync → 统一 SKU Schema
                                                  ↓
                                          平台统一 SKU 数据库
                                                  ↓
                                    Skill / 编排层只看到标准化数据
```

**一句话：CLI 层的核心价值之一就是"把非标的现实世界，统一成标准接口"，这是架构设计的基本功而非附加功能。**

---

### 总结

| 风险 | 我们的核心应对 |
|------|-------------|
| 确定性与容错 | LLM 只做调度，计算和数据来自确定性专业系统，关键节点有人工确认 |
| 长周期状态管理 | 数据库是唯一真相，LLM 每次从库中读取最新状态，不依赖对话记忆 |
| 算力成本与延迟 | 分级策略：简单查询不过LLM，复杂任务异步处理，部分模型私有化部署 |
| GUI 局限性 | LUI + GUI 融合，CLI 是底层封装不是用户界面，视觉化工具作为独立子系统集成 |
| 供应链集成 | CLI 标准化层屏蔽异构差异，渐进式接入，提供供应商协同工具 |

这个架构的本质思路是：**用"智能编排"把"专业系统"串起来**——智能在于编排的灵活性，可靠在于每个原子能力的确定性。我们不是在让 AI 替代专业系统，而是让 AI 帮助人更高效地使用这些专业系统。
