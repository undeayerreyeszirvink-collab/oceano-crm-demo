# 场景化能力设计示例：N 个企业业务场景

> 说明：本文档将 `N` 默认落为 8 个高频企业场景，覆盖财务、采购、销售、客服、HR、营销、库存与门店导购等典型岗位。每个场景均采用统一分析框架：
>
> `业务请求 -> 输入资料 -> Ontology -> L1/L2/L3 Skills -> Agent 编排 -> CLI Gateway -> Human-in-the-Loop -> 业务结果`

---

## 1. 财务场景：员工报销申请

### 1.1 业务请求

员工在企业微信中发送：

“帮我报销昨天客户拜访的打车费和午餐费，发票已经上传。”

### 1.2 输入资料

- 结构化数据：员工主数据、成本中心、历史报销单、预算余额、审批关系
- 非结构化文档：报销制度、财务 SOP、差旅规范、招待费规则

### 1.3 Ontology 关注点

- 实体：员工、发票、报销单、费用类型、成本中心、审批人
- 关系：员工属于部门、报销单归属成本中心、费用类型对应审批规则
- 规则：超金额阈值需审批、招待费需补充陪同人员、差旅费需交叉验证

### 1.4 Skills 分层

- L1：意图识别、发票字段抽取、表单草稿生成、澄清追问
- L2：费用分类、报销规则预检、票据有效性检查、审批阈值判断
- L3：`employee-reimbursement-process`

### 1.5 Agent 编排

1. 识别报销意图并抽取发票信息
2. 注入成本中心、费用规则、审批关系等业务上下文
3. 调用 L3 报销流程 Skill，编排 L2 校验能力
4. 发现信息缺失时追问用户
5. 满足规则后准备提交 ERP / OA

### 1.6 CLI Gateway

- 查询 ERP 历史费用明细
- 创建报销审批单
- 提交报销记录
- 写入审计日志

### 1.7 Human-in-the-Loop

- 招待费信息不完整时要求员工补充
- 超金额阈值时推送主管审批卡片

### 1.8 业务结果

- 报销单生成
- 审批链启动
- 用户收到单号、金额、状态回执

## 2. 采购场景：紧急采购申请

### 2.1 业务请求

采购专员发送：

“市场部活动下周要用 200 份展示物料，库存不够，帮我尽快发起采购，优先找能 3 天内到货的老供应商。”

### 2.2 输入资料

- 结构化数据：库存台账、供应商主数据、采购订单、预算信息、历史价格
- 非结构化文档：采购制度、紧急采购 SOP、供应商准入规范、预算审批规则

### 2.3 Ontology 关注点

- 实体：物料、库存、采购申请、供应商、预算、审批节点
- 关系：供应商供应物料、部门占用预算、采购申请关联供应商和预算
- 规则：库存不足才允许采购、紧急采购可走绿色通道、新供应商需准入

### 2.4 Skills 分层

- L1：需求抽取、表单生成、澄清追问
- L2：库存核查、供应商匹配、预算校验、比价评估
- L3：`event-material-urgent-procurement`

### 2.5 Agent 编排

1. 识别为紧急采购需求
2. 注入库存规则、供应商准入、预算约束等上下文
3. 调用 L2 能力核查库存与可选供应商
4. 由 L3 Skill 组织比价、选型、审批与下单准备

### 2.6 CLI Gateway

- 查询 WMS 库存
- 查询 ERP 预算
- 查询 SRM 供应商和交期
- 创建 OA / ERP 采购申请

### 2.7 Human-in-the-Loop

- 推荐供应商方案需采购专员确认
- 紧急采购需部门负责人确认预算占用

### 2.8 业务结果

- 采购申请单生成
- 推荐供应商与交付时间输出
- 审批流进入执行

## 3. 销售场景：客户特殊折扣申请

### 3.1 业务请求

销售发送：

“客户华星科技这单想申请 85 折，帮我走一下特批，客户说今天确认就能下单。”

### 3.2 输入资料

- 结构化数据：CRM 客户主档、报价单、历史成交价、毛利率、审批记录
- 非结构化文档：折扣制度、报价 SOP、大客户例外规则、渠道价格保护规范

### 3.3 Ontology 关注点

- 实体：客户、报价单、折扣、毛利率、审批人、商机
- 关系：客户对应等级、报价关联产品和毛利、审批人对应授权层级
- 规则：低于授权线需升级审批、低于毛利红线需总监审批、渠道价不得突破保护线

### 3.4 Skills 分层

- L1：请求理解、字段抽取、特批理由补充
- L2：客户等级识别、折扣预检、毛利评估、审批路由判断
- L3：`special-discount-approval-process`

### 3.5 Agent 编排

1. 判断为折扣特批场景
2. 注入客户等级、授权边界、渠道约束
3. 调用 L2 评估折扣影响
4. 由 L3 Skill 组织特批流程与审批路径

### 3.6 CLI Gateway

- 查询 CRM 客户信息与历史订单
- 查询 CPQ / 报价系统底价和授权价
- 创建 OA 特批单并更新报价权限

### 3.7 Human-in-the-Loop

- 销售补充竞争信息和成交必要性
- 区域经理和销售总监审批

### 3.8 业务结果

- 特批申请提交
- 审批通过后报价权限更新
- 销售收到有效期和折扣结果

## 4. 客服场景：投诉工单升级处理

### 4.1 业务请求

客服人员收到用户投诉：

“上周买的产品已经坏了两次，你们再不给解决我就去投诉平台曝光。”

### 4.2 输入资料

- 结构化数据：客户档案、订单记录、售后记录、SLA、工单状态
- 非结构化文档：客服 SOP、投诉升级规则、赔付政策、话术规范

### 4.3 Ontology 关注点

- 实体：客户、订单、工单、投诉等级、赔付方案、升级节点
- 关系：客户关联订单和历史工单、投诉等级决定升级路由
- 规则：重复故障、公开投诉风险、高价值客户应优先升级

### 4.4 Skills 分层

- L1：意图识别、情绪识别、摘要生成、回复草稿生成
- L2：投诉分级、SLA 判断、赔付建议、升级路由判断
- L3：`customer-complaint-escalation-process`

### 4.5 Agent 编排

1. 识别为高风险投诉
2. 注入客户等级、历史故障次数、赔付规则
3. 判断是否需要立即升级
4. 自动生成回复建议和内部处理路径

### 4.6 CLI Gateway

- 查询 CRM / 售后系统历史记录
- 创建工单升级任务
- 通知售后与主管处理

### 4.7 Human-in-the-Loop

- 高风险赔付金额需主管确认
- 超 SLA 需人工复核处理优先级

### 4.8 业务结果

- 工单升级
- 客服获得回复建议
- 用户获得明确处理承诺

## 5. HR 场景：Offer 审批与发放

### 5.1 业务请求

招聘专员发送：

“候选人张敏面试通过，岗位是高级产品经理，帮我发起 Offer 审批。”

### 5.2 输入资料

- 结构化数据：岗位编制、薪资带宽、候选人信息、面试结果、审批链
- 非结构化文档：招聘流程 SOP、薪酬制度、Offer 审批规则、例外条款

### 5.3 Ontology 关注点

- 实体：候选人、岗位、编制、薪资、审批人、Offer
- 关系：岗位对应职级和薪资范围、审批人对应组织层级
- 规则：超薪资带宽需特批、HC 不足不得发 Offer、关键岗位需双重审批

### 5.4 Skills 分层

- L1：候选人信息整理、表单生成、缺失字段追问
- L2：编制校验、薪资带宽校验、审批链匹配
- L3：`offer-approval-process`

### 5.5 Agent 编排

1. 核对岗位、候选人和薪资建议
2. 注入编制约束、薪资规则和审批层级
3. 由 L3 Skill 组织 Offer 审批流程

### 5.6 CLI Gateway

- 查询 HRIS 编制情况
- 创建 Offer 审批单
- 发起电子 Offer 草稿

### 5.7 Human-in-the-Loop

- 超带宽薪资需 HRBP / 业务负责人特批
- 信息不全时要求招聘专员补充

### 5.8 业务结果

- Offer 审批启动
- 审批通过后生成正式 Offer

## 6. 营销场景：活动线索跟进与分发

### 6.1 业务请求

市场人员发送：

“昨天活动收了 300 条线索，帮我按行业和成交可能性分组，分给销售团队跟进。”

### 6.2 输入资料

- 结构化数据：线索表、客户标签、历史转化率、销售归属规则
- 非结构化文档：线索评分 SOP、行业标签定义、分配规则、跟进规范

### 6.3 Ontology 关注点

- 实体：线索、客户、行业、销售团队、评分、跟进阶段
- 关系：线索归属行业、销售团队负责特定区域或行业
- 规则：高分线索优先分配、战略行业优先资深销售、重复线索不得重复建档

### 6.4 Skills 分层

- L1：字段清洗、去重、摘要生成
- L2：线索评分、行业归类、销售匹配
- L3：`campaign-lead-routing-process`

### 6.5 Agent 编排

1. 处理活动导出线索
2. 注入线索评分标准和分配规则
3. 按优先级、区域、行业进行自动路由

### 6.6 CLI Gateway

- 写入 CRM 线索池
- 创建销售跟进任务
- 更新线索归属

### 6.7 Human-in-the-Loop

- 战略客户线索需销售经理确认归属
- 数据冲突时由市场运营人工复核

### 6.8 业务结果

- 线索完成清洗、分组、分发
- 销售收到待跟进清单

## 7. 库存场景：缺货替代与调拨建议

### 7.1 业务请求

库存管理员发送：

“A 区仓的这款产品快断货了，帮我找相似可替代产品，并看看其他仓有没有可调拨库存。”

### 7.2 输入资料

- 结构化数据：SKU、库存量、仓库分布、历史替代关系、销售速度
- 非结构化文档：调拨规则、替代策略、库存安全线说明

### 7.3 Ontology 关注点

- 实体：SKU、仓库、库存、安全线、替代 SKU、调拨单
- 关系：SKU 与替代 SKU 的相似关系、仓库之间的调拨关系
- 规则：低于安全线触发预警、优先同城调拨、替代品需满足兼容性

### 7.4 Skills 分层

- L1：预警识别、信息汇总、任务草稿生成
- L2：库存风险评估、替代 SKU 匹配、调拨建议生成
- L3：`stock-reallocation-and-substitution-process`

### 7.5 Agent 编排

1. 识别库存预警
2. 注入安全线规则和仓间调拨约束
3. 先判断是否可调拨，再判断是否建议替代

### 7.6 CLI Gateway

- 查询 WMS 多仓库存
- 创建调拨单
- 更新替代建议到订单系统

### 7.7 Human-in-the-Loop

- 替代 SKU 是否接受需业务方确认
- 大批量调拨需仓储主管审批

### 7.8 业务结果

- 输出调拨建议和替代方案
- 系统内生成调拨任务

## 8. 门店导购场景：客户找相似产品并生成成交方案

### 8.1 业务请求

门店导购对系统说：

“客户拿来一张别人家的产品图，帮我找我们店里最接近的可售款，再给一份报价和搭配建议。”

### 8.2 输入资料

- 结构化数据：商品目录、价格、库存、历史成交数据、搭配规则
- 非结构化文档：导购 SOP、竞品替代话术、套餐销售规则、风格搭配手册

### 8.3 Ontology 关注点

- 实体：客户、目标产品、替代产品、价格方案、搭配件、门店库存
- 关系：产品与风格、产品与搭配件、门店与库存
- 规则：优先推荐现货、可用替代品需满足风格和价格带相近、套餐需满足最低毛利要求

### 8.4 Skills 分层

- L1：图片理解、需求抽取、报价草稿生成
- L2：相似产品匹配、价格带评估、搭配推荐
- L3：`in-store-similar-product-conversion-process`

### 8.5 Agent 编排

1. 识别客户目标风格和预算意向
2. 注入门店库存、搭配规则和价格约束
3. 从相似产品中优先选择可售且现货的方案
4. 自动生成主推方案、平替方案和搭配建议

### 8.6 CLI Gateway

- 查询门店库存
- 查询价格和促销活动
- 生成报价单

### 8.7 Human-in-the-Loop

- 导购确认最终推荐方案
- 特殊折扣或套餐价需店长确认

### 8.8 业务结果

- 输出成交方案
- 导购获得可直接展示给客户的报价与搭配建议

## 9. 统一抽象：N 个场景的共用执行骨架

上述 8 个场景虽然分属不同部门，但在平台内部遵循同一套能力编排逻辑：

1. 用户以自然语言、表单或附件发起业务请求
2. 平台从结构化数据和非结构化文档中抽取或注入 Ontology 上下文
3. `L1` 负责理解、抽取、澄清和结构化
4. `L2` 负责行业通用判断、校验、匹配和评估
5. `L3` 负责企业专属 SOP 与流程编排
6. `CLI Gateway` 负责受控访问业务系统并执行查询或写操作
7. `Human-in-the-Loop` 负责补充信息、审批和异常决策
8. 任务完成后返回业务结果，并写入审计和状态系统

这意味着平台真正沉淀的不是单点 Agent，而是一套可跨岗位复用的“业务理解层 + 能力层 + 编排层 + 执行层”。

## 10. 后续扩展建议

- 法务：合同审核与盖章申请

- 售后：返修、补件与赔付流程
- 门店：客户补单与旧款替代推荐

建议下一步将每个场景进一步细化为：

- 对应的 Ontology 实体-关系模型
- Skill 清单与依赖图
- CLI 命令定义
- Human-in-the-Loop 状态机
- 端到端时序图

## 11. 美妆生产场景：新品打样与配方评审

### 11.1 业务请求

产品经理发送：

“这款敏感肌修护面霜准备进入打样，帮我拉起配方评审流程，并核对原料合规性和预计打样周期。”

### 11.2 输入资料

- 结构化数据：原料库、配方版本、供应商信息、打样排期、历史打样记录
- 非结构化文档：配方开发 SOP、原料禁限用清单、敏感肌产品规范、评审流程制度

### 11.3 Ontology 关注点

- 实体：产品、配方、原料、供应商、评审单、打样任务
- 关系：配方由原料组成、原料对应供应商、产品对应功效宣称
- 规则：敏感肌产品禁用特定成分、打样前需完成法规与研发双评审

### 11.4 Skills 分层

- L1：需求抽取、资料汇总、缺失字段追问
- L2：原料合规校验、配方风险识别、打样周期评估
- L3：`cosmetics-formula-sampling-review-process`

### 11.5 Agent 编排

1. 识别为新品打样发起
2. 注入原料限制、宣称要求、研发评审规则
3. 调用 L2 做原料和配方预检
4. 由 L3 Skill 组织配方评审与打样排期流程

### 11.6 CLI Gateway

- 查询 PLM / 配方系统原料与版本
- 创建打样评审单
- 写入研发排期系统

### 11.7 Human-in-the-Loop

- 法规风险项需法规负责人确认
- 高风险原料替换需研发经理审批

### 11.8 业务结果

- 打样评审单生成
- 配方风险清单输出
- 打样计划进入执行

## 12. 美妆生产场景：批次异常与质量放行

### 12.1 业务请求

质检主管发送：

“这批精华液灌装后黏度偏高，帮我判断是否需要拦截放行，并生成异常处理流程。”

### 12.2 输入资料

- 结构化数据：批次记录、质检结果、工艺参数、设备日志、历史异常案例
- 非结构化文档：质检 SOP、放行标准、偏差处理规范、CAPA 模板

### 12.3 Ontology 关注点

- 实体：批次、质检项目、工艺参数、异常单、放行状态
- 关系：批次关联工艺参数和质检结果、异常关联纠正措施
- 规则：关键指标超限需冻结批次、放行前需完成偏差评估

### 12.4 Skills 分层

- L1：检测结果汇总、异常摘要生成
- L2：偏差识别、风险等级判断、放行条件校验
