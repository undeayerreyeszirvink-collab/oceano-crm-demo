# 欧神诺 AI 数字员工平台 — 技术实现方案

**版本：** V1.0 | **日期：** 2026-03-26

---

## 一、项目总体思路

### 1.1 核心原则

1. **平台先行，智能体分批上线：** 搭建数字员工平台底座的同时启动首个智能体开发，确保每个智能体上线即能在企微中运行、被管理、被评估。
2. **以业务价值驱动优先级：** 优先交付对盈利影响最直接的智能体，快速产生可量化的经营改善。
3. **两组并行、流水线作业：** A 组（平台架构）和 B 组（业务调研+Skill/Tool 开发）交替配合，A 组产出平台能力，B 组消费平台能力交付业务智能体。
4. **不等不靠、即刻启动：** 合同签订和需求确认阶段即启动技术 POC 和平台底座搭建，不浪费等待时间。

### 1.2 智能体交付顺序与理由

| 顺序 | 智能体 | 交付时段 | 优先级理由 |
|------|--------|---------|-----------|
| 1 | 工程报价与审批智能体 | 第 3-4 月 | 直接提升工程毛利 3%-5%，见效最快，数据依赖相对简单（BIP 成本数据+产品库），是甲方管理层最关注的指标 |
| 2 | 经销商营销智能体 | 第 5-6 月 | 营销内容生成和渠道分析是甲方核心诉求，紧跟报价智能体上线可形成"报价→营销"联动效应；尽早上线给经销商推广留出充足运营时间 |
| 3 | 采购智能体 | 第 7-8 月 | 原材料采购金额大，3%-5% 的成本优化直接反映在利润表，与工程报价共享成本数据底座 |
| 4 | 供应链智能协同大脑 | 第 9-10 月 | 需要前面智能体的数据基础（产品成本、渠道库存、采购计划），是"以销定产"的枢纽 |
| 5 | 生产管控智能体 | 第 10-12 月 | 依赖 IoT 设备接入和产线现场配合，准备周期最长，放在最后给甲方更多硬件部署时间 |

## 二、技术架构方案

### 2.1 技术栈选型

| 层级 | 技术选型 | 说明 |
|------|---------|------|
| **LLM 层** | Claude API (主) + 国产大模型备用 | Claude 作为主力推理引擎；备用国产模型（如 DeepSeek / Qwen）用于成本敏感的批量任务（如营销文案生成） |
| **Agent 框架** | 类 OpenClaw 自研框架 | 基于 Skill/Tool 编排机制，支持主动任务引擎、记忆管理、多轮对话 |
| **后端服务** | Python (FastAPI) | 统一使用 Python 技术栈：Agent 编排、API 网关、企微消息接入、SQL Proxy、BIP Gateway 全部基于 FastAPI |
| **数据连接** | SQL Proxy (Greenplum) + BIP API Gateway | SQL Proxy 做安全校验+查询代理；BIP Gateway 封装用友 REST API |
| **指标语义层** | 自研 get_metric_sql 工具 | 预定义指标模板（计算口径+可用维度），LLM 选指标+维度，工具返回正确 SQL |
| **向量数据库** | Milvus / pgvector | 产品图像特征向量（SKU 聚类）、文档嵌入（合同分析）、知识库检索 |
| **消息队列** | Redis Streams / RabbitMQ | 主动任务调度、事件驱动触发、异步任务处理 |
| **前端** | React (管理后台) + 企微原生 (交互端) | 管理后台用于数字员工管理、绩效看板；用户侧全部通过企微交互 |
| **数据库** | PostgreSQL (业务数据) + Redis (缓存/会话) | 存储数字员工配置、权限、审计日志、对话记忆 |
| **部署** | Docker + K8s (甲方私有云) | 容器化部署，支持弹性扩缩容；敏感数据不出甲方网络 |
| **监控** | Prometheus + Grafana + 自研 Token 计量 | 系统可用性监控 + LLM 用量统计 + 业务指标看板 |
| **CV 模型** | CLIP / DINOv2 + 微调 | 产品图像特征提取，用于竞品对标和 SKU 聚类 |

### 2.3 关键技术设计

#### 2.3.1 SQL Proxy 安全机制

```
LLM 生成 SQL → SQL Proxy 校验层：
  ① 仅允许 SELECT 语句（拒绝 INSERT/UPDATE/DELETE/DROP）
  ② 表白名单校验（只允许访问授权表）
  ③ 自动注入 LIMIT（防止全表扫描拖垮数仓）
  ④ 列级脱敏（敏感字段如手机号自动掩码）
  ⑤ 超时控制（单次查询 ≤ 30s）
→ 执行查询 → 结果返回 LLM
```

#### 2.3.2 BIP 写操作二次确认 (prepare/submit)

```
用户："帮我把这批订单的交货日期改为下周五"
  → LLM 调用 bip_prepare_update_delivery(order_ids, new_date)
  → 系统返回变更预览卡片（包含影响范围、变更内容摘要）
  → 用户在企微中点击"确认执行"
  → 系统调用 bip_submit_update_delivery(confirmation_token)
  → 执行写入并返回结果
```

#### 2.3.3 主动任务引擎

| 模式 | 实现方式 | 典型场景 |
|------|---------|---------|
| 定时巡检 | Cron + Redis Streams | 每日 8:00 推送现金头寸报告；每周一推送供应商风险变动 |
| 事件触发 | BIP Webhook + 消息队列 | 新工程订单进入 → 自动触发报价预核算 |
| 阈值预警 | 定时轮询 + 阈值规则引擎 | 库存低于安全水位 → 自动推送补货建议 |
| 定期报告 | Cron + 模板化 Skill | 周五下午自动生成本周竞品动态简报 |
| 跟进提醒 | 状态机 + 延时队列 | 报价单超 48h 未审批 → 提醒审批人 |
