## 1. 场景总述

### 1.1 业务目标

某瓷砖生产企业的订单策略管理部，需要在工程定制订单进入后，快速、可追溯地完成“选厂决策”。  
该决策并不是一个简单的价格比较问题，而是一个多目标、多约束、多系统、多角色参与的综合决策过程。

需要同时综合考虑：

- 可生产品类
- 动态价格体系
- 排产优先级
- 交付省份与运输成本
- 工厂排期
- 库存与返工库存
- 产品工艺与编码匹配关系
- 政策倾斜与动态调整

### 1.2 为什么这个场景适合做 Agent

因为它天然具备以下特征：

- 强依赖结构化与非结构化数据混合计算
- 规则并不只存在于表格里，还存在于 Word 政策文档里
- 决策链条较长，人工反复跨表比对成本高
- 需要解释过程，不能只给结果
- 存在高毛利与参数调整之间的博弈，需要人与系统协同

这意味着它非常适合设计为：

`Ontology + L1/L2/L3 Skills + Agent 编排 + CLI 对接 + Human-in-the-Loop`

## 2. 统一前置条件

以下条件未满足时，系统只能提供“辅助建议”，不得直接闭环执行：

| 条件项 | 最低要求 | 不满足时的处理方式 |
|---|---|---|
| 产品编码标准 | 同一产品编码在各系统中含义一致 | 仅输出低可信建议 |
| 工艺映射规则 | 产品编码到工艺的映射完整可用 | 不执行成本试算 |
| 库存口径统一 | BIP 库存与返工台账有可合并规则 | 不输出真实可用库存 |
| 厂家主数据完整 | 厂家能力、地址、交付省份、价格规则可查询 | 不做自动选厂 |
| 价格规则可解析 | 文字型加价规则可结构化抽取 | 不做最终毛利排序 |
| 政策版本可追踪 | 每次策略调整有生效时间和版本号 | 不支持自动重算 |
| CLI 可调用 | BIP / 排产 / 价格 / 库存系统可受控读写 | 不做结果回写 |

## 3. 场景拆分

基于调研报告，推荐将“工程定制订单选厂”拆为 4 个核心子场景：

1. 常规工程定制订单智能选厂
2. 真实可用库存核算与排产可行性判断
3. 参数可调条件下的高毛利沟通建议
4. 政策调整后的订单策略重算

这样拆分的原因是：

- 场景 1 解决“如何给出初步厂家排序”
- 场景 2 解决“库存和排期是否真的支持该排序”
- 场景 3 解决“当最优厂家差一点参数时，如何辅助业务沟通”
- 场景 4 解决“当政策变化时，如何快速重算并留痕”

## 4. 场景一：常规工程定制订单智能选厂

### 4.1 场景描述

经销商或自营工程项目提交一笔常规定制订单，订单策略管理部需要根据产品规格、尺寸、价格、交付省份、交付时间和工厂策略，快速输出可行厂家名单和毛利排序。

### 4.2 业务触发

- BIP 中有新的工程定制订单进入中间表
- 订单类型属于“常规订单”
- 不属于“客户指定生产”或“客户指定采购”

### 4.3 Ontology 提取

#### 实体

- 订单
- 订单类型
- 产品编码
- 工艺
- 厂家
- 厂家类型
- 规格
- 尺寸
- 交付省份
- 交付时间
- 基准价
- 加价规则
- 毛利率
- 排产策略版本

#### 角色

- 经销商下单人
- 订单策略专员
- 订单管理部
- 工厂排产人员
- 审核人

#### 关系

- 订单对应产品编码与规格
- 产品编码映射工艺
- 工艺决定可生产厂家范围
- 厂家对应价格、地址、交付省份和优先级
- 排产策略版本影响厂家优先顺序

#### 状态

- 待解析
- 待试算
- 待排序
- 待人工确认
- 已输出选厂结果
- 已驳回 / 需补充信息

#### 规则

- 特殊订单不参与普通选厂逻辑
- 指定生产 / 指定采购订单不进入比选流程
- 厂家必须满足规格、尺寸、品类可生产能力
- 毛利排序必须结合运费与加价规则，而不是只看出厂价
- 输出结果必须附带可解释理由

#### 事件

- 订单进入
- 订单类型识别
- 数据补全
- 试算完成
- 排序完成
- 人工确认

### 4.4 Skills 定义

#### L1

- `order-intent-and-type-detection`
- `order-field-extraction`
- `pricing-rule-text-extraction`
- `result-summary-generation`

#### L2

- `factory-capability-match`
- `gross-margin-simulation`
- `delivery-province-fit-check`
- `policy-priority-evaluation`

#### L3

- `tenant-engineering-order-factory-selection-process`

定义：

- 负责某瓷砖生产企业常规工程定制订单的“解析 -> 试算 -> 排序 -> 解释 -> 提交确认”完整流程
- 编排多个 L2 模块，并控制是否允许写回订单结果

### 4.5 Agent 平台编排

1. 监听 BIP 中间表新订单
2. L1 识别订单类型并抽取关键字段
3. 调用 Ontology 注入厂家、工艺、策略、价格语义
4. L2 先做厂家能力匹配，再做毛利试算和交付适配
5. 若缺失关键字段，转人工补充
6. 加载 `tenant-engineering-order-factory-selection-process`
7. 输出候选厂家清单、毛利排序、排除原因、建议结论
8. 等待人工确认后，将结果同步给订单管理部

### 4.6 CLI 对接

只读 CLI：

- `bip.order.customized.get`
- `product.process.mapping.get`
- `factory.capability.matrix.get`
- `pricing.rule.table.get`
- `policy.strategy.current.get`

写入 CLI：

- `order.factory-selection.result.create`
- `order.factory-selection.comment.create`
- `order.management.sync`

### 4.7 Human-in-the-Loop

- 当订单类型识别存在歧义时，订单策略专员确认
- 当毛利最高方案与当前政策存在冲突时，由审核人拍板
- 当候选厂家都存在明显缺口时，由业务人员介入处理

### 4.8 输出示例

系统不应只输出“选 A 厂”，而应输出：

- 推荐厂家：A 厂
- 候选顺位：A 厂 > B 厂 > 自有基地
- 推荐原因：规格匹配、交付省份优先、综合毛利最高
- 排除原因：C 厂无对应品类；D 厂排期冲突
- 是否需人工确认：是 / 否

## 5. 场景二：真实可用库存核算与排产可行性判断

### 5.1 场景描述

在制定生产计划时，系统不能只看 BIP 中的库存，还要结合线下返工台账，计算真实可用库存，并判断当前订单是否可以优先排产、转采购，或需要进一步协调。

### 5.2 业务触发

- 常规订单需要进入选厂或排产
- 当前产品存在库存相关判断需求
- BIP 库存与线下返工台账均有记录

### 5.3 Ontology 提取

#### 实体

- 库存
- 可用库存
- 锁定库存
- 返工库存
- 线下返工台账
- 订单需求量
- 排产能力
- 采购可替代路径

#### 角色

- 订单策略专员
- 仓储人员
- 生产计划员
- 订单管理部

#### 关系

- 可用库存 = 系统库存与返工锁定规则计算后的结果
- 返工库存不等于可直接使用库存
- 库存与排期共同决定是否可排产
- 排产困难时可切换采购判断路径

#### 状态

- 库存充足
- 库存不足
- 库存待校验
- 可排产
- 需采购
- 需人工处理

#### 规则

- 真实库存必须结合 BIP 与返工台账计算
- 未完成库存校验不得输出确定性排产结论
- 排产困难时才允许进入采购替代分支

#### 事件

- 订单进入库存核算
- 线下返工台账更新
- 库存校验完成
- 生成排产 / 采购建议

### 5.4 Skills 定义

#### L1

- `inventory-data-normalization`
- `offline-ledger-field-extraction`
- `stock-calculation-summary`

#### L2

- `real-available-stock-calculation`
- `rework-lock-impact-evaluation`
- `production-vs-procurement-feasibility-check`

#### L3

- `tenant-available-stock-and-scheduling-feasibility-process`

定义：

- 负责某企业工程定制订单场景下的库存核算、返工锁定合并、排产可行性判断和采购分支切换

### 5.5 Agent 平台编排

1. 读取订单需求量和产品编码
2. L1 统一 BIP 库存和线下返工台账字段
3. L2 计算真实可用库存并判断返工库存占用影响
4. 判断是否满足排产条件
5. 若不满足，进入“采购可行性”分支
6. 若库存数据存在冲突，触发人工复核
7. 输出“可排产 / 可采购 / 待人工确认”的建议结论

### 5.6 CLI 对接

只读 CLI：

- `bip.inventory.get`
- `offline.rework-ledger.get`
- `factory.schedule.capacity.get`

写入 CLI：

- `order.stock-feasibility.result.create`
- `schedule.review.task.create`

### 5.7 Human-in-the-Loop

- 返工台账与系统库存冲突时，由仓储或计划人员复核
- 排产困难但采购替代风险高时，由订单策略专员确认分支

### 5.8 输出示例

- 真实可用库存：820 平
- 返工锁定库存：160 平
- 当前订单需求：1000 平
- 建议：库存不足，不建议直接排产；可进入采购路径评估

## 6. 场景三：参数可调条件下的高毛利沟通建议

### 6.1 场景描述

当综合测算发现某一厂家毛利更优，但其坯体厚度、吸水率等“次要参数”与客户要求存在轻微偏差时，系统需要判断这些偏差是否属于可沟通调整范围，并为业务员提供建议话术和替代方案。

### 6.2 业务触发

- 已完成厂家候选排序
- 第一优选厂家在次要参数上存在偏差
- 报告中定义该类偏差需要与客户沟通，而非直接淘汰

### 6.3 Ontology 提取

#### 实体

- 厂家候选方案
- 次要参数
- 核心参数
- 参数偏差
- 毛利差额
- 客户沟通方案
- 替代建议

#### 角色

- 订单策略专员
- 销售 / 客户沟通人员
- 客户
- 审核人

#### 关系

- 厂家候选方案对应参数差异
- 参数分为核心与非核心
- 非核心参数可进入沟通建议路径
- 毛利提升空间与沟通必要性相关

#### 状态

- 完全匹配
- 轻微偏差可沟通
- 偏差不可接受
- 待客户确认
- 已确认调整
- 已放弃该方案

#### 规则

- 核心参数不允许建议修改
- 非核心参数的可调范围需配置化管理
- 沟通建议必须展示“收益”和“偏差”两侧信息
- 未经人工确认不得自动替客户改参数

#### 事件

- 候选方案生成
- 参数偏差识别
- 沟通建议生成
- 客户确认结果返回

### 6.4 Skills 定义

#### L1

- `parameter-diff-extraction`
- `candidate-scheme-summary`
- `customer-communication-draft`

#### L2

- `core-vs-secondary-parameter-classification`
- `margin-uplift-estimation`
- `parameter-adjustability-evaluation`

#### L3

- `tenant-order-parameter-adjustment-suggestion-process`

定义：

- 负责某企业在工程定制订单场景下，对“可调参数”方案进行收益评估、沟通建议生成和确认闭环

### 6.5 Agent 平台编排

1. 读取候选厂家排序结果
2. L1 抽取参数差异和收益差额
3. L2 判断偏差是否属于“非核心可沟通参数”
4. 若可沟通，则生成多套建议方案
5. L3 组织“内部确认 -> 对客沟通 -> 结果回传”的流程
6. 根据客户反馈重新确认厂家选择

### 6.6 CLI 对接

只读 CLI：

- `factory.candidate.scheme.get`
- `product.spec.rule.get`
- `policy.parameter-adjustment.rule.get`

写入 CLI：

- `customer-adjustment-suggestion.record.create`
- `order.factory-selection.recalculate`

### 6.7 Human-in-the-Loop

- 业务员确认是否对客户发出调整建议
- 客户确认是否接受参数微调
- 审核人确认该调整是否符合公司对外承诺边界

### 6.8 输出示例

- 当前最优毛利厂家：A 厂
- 与客户需求偏差：吸水率偏差 0.2%，属于可沟通范围
- 建议动作：由销售向客户提出“交付周期不变、价格更优”的替代方案
- 若客户拒绝：回退到 B 厂方案

## 7. 场景四：政策调整后的订单策略重算

### 7.1 场景描述

当公司突然调整策略，例如阶段性向某类厂家倾斜、控制某地区运输成本、优先消化某基地产能时，系统需要支持业务人员通过自然语言或结构化输入快速注入新策略，并对尚未定版的订单重新计算厂家建议。

### 7.2 业务触发

- 策略文档更新
- 管理层口头或书面下发临时倾斜政策
- 业务人员发起“按新政策重算”请求

### 7.3 Ontology 提取

#### 实体

- 策略版本
- 策略规则
- 生效时间
- 厂家优先级
- 订单池
- 重算结果

#### 角色

- 订单策略专员
- 部门负责人
- 订单管理部
- 审核人

#### 关系

- 策略版本作用于订单池
- 订单池中的未定版订单可被重算
- 不同策略版本之间必须可追溯

#### 状态

- 现行策略
- 新策略待生效
- 待重算
- 重算完成
- 待确认
- 已发布

#### 规则

- 每次策略变更必须生成版本号和生效时间
- 重算结果必须标明“相较旧策略”的差异原因
- 已执行下游生产的订单不得直接重算覆盖

#### 事件

- 策略更新
- 触发重算
- 差异生成
- 人工确认
- 发布结果

### 7.4 Skills 定义

#### L1

- `policy-text-extraction`
- `policy-change-diff-summary`
- `resimulation-request-parsing`

#### L2

- `policy-rule-structuring`
- `order-impact-scope-evaluation`
- `strategy-diff-explanation`

#### L3

- `tenant-policy-change-order-resimulation-process`

定义：

- 负责某企业订单策略更新场景下的策略注入、影响范围识别、订单重算与结果留痕

### 7.5 Agent 平台编排

1. 接收新的策略文档或自然语言策略输入
2. L1 抽取变更内容
3. L2 将非结构化策略转为结构化规则，并评估受影响订单池
4. L3 组织重算流程，比较新旧结果差异
5. 输出“哪些订单变化、为什么变化、是否需要人工确认”
6. 经人工确认后，将新版策略结果同步下游

### 7.6 CLI 对接

只读 CLI：

- `policy.strategy.document.get`
- `order.pool.pending.get`
- `order.factory-selection.history.get`

写入 CLI：

- `policy.strategy.version.create`
- `order.factory-selection.batch-resimulate`
- `order.strategy-change.audit.record.create`

### 7.7 Human-in-the-Loop

- 部门负责人确认策略变更是否正式生效
- 审核人确认重算订单范围
- 对涉及重大利润变化的订单进行人工二次确认

### 7.8 输出示例

- 新策略：华东区域订单优先自有基地
- 受影响订单：42 单
- 重算后变化：17 单从外协厂切换至自有基地
- 主要原因：运输成本下降 + 基地优先级提升

## 8. Agent 平台统一编排骨架

这个业务域不应该做成一个“万能大 Agent”，而应该按统一骨架拆解：

1. 订单 / 策略 / 库存事件接入
2. Ontology 上下文注入
3. L1 提取与标准化
4. L2 判断、试算、评估、解释
5. L3 流程编排
6. CLI 查询 / 写回
7. Human-in-the-Loop
8. 留痕、回写、复盘

这意味着：

- Agent 平台是编排者
- L1 / L2 / L3 是能力层
- CLI 是执行层
- 人工确认是关键控制层

## 9. CLI 设计建议

建议对该业务域的 CLI 做统一治理。

### 9.1 命名建议

采用：

`<domain>.<object>.<action>`

示例：

- `order.customized.get`
- `factory.selection.result.create`
- `inventory.real-available.calculate`
- `policy.strategy.version.create`
- `order.factory-selection.batch-resimulate`

### 9.2 CLI 元数据要求

每个 CLI 至少定义：

- `command_name`
- `input_schema`
- `output_schema`
- `permission_scope`
- `idempotency_key`
- `side_effect_level`
- `audit_fields`

### 9.3 风险控制

- 订单结果写回必须可追溯
- 批量重算必须支持回滚或版本对照
- 库存核算与参数调整建议不得绕过人工确认直接修改客户承诺

---

## 10. 这份场景设计的核心价值

与“直接做个智能选厂页面”相比，本设计的价值在于：

- 先把对象、规则、状态和事件用 Ontology 固化
- 再把能力拆成 `L1 / L2 / L3`
- 再由 Agent 平台按场景编排
- 最后才通过 CLI 连接现有系统

这样设计后，系统才具备：

- 可解释性
- 可追溯性
- 可演进性
- 可审计性
