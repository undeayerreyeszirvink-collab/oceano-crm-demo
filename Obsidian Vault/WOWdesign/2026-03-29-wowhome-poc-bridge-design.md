# WowHome POC 桥接设计文档

**日期：** 2026-03-29  
**状态：** 待审阅草稿  
**形成方式：** 基于 Superpowers `brainstorming` 方法整理

## 1. 文档目的

这份文档用于连接当前的 WowHome 长期愿景与当前的 POC 定义。

它要回答的核心问题是：

`为什么当前这个 POC，是通向 WowHome 长期操作系统愿景的正确第一步？`

答案是：

当前 POC 不是完整平台的缩小版，而是平台的第一层基础能力：

**需求翻译层（demand translation layer）**

## 2. 定位

### 面向用户的定位

`AI 理解你和你的家`

这是用户应该感受到的产品语言。产品对用户来说，应该像一个真正理解其家庭、习惯、张力关系和理想生活方式的系统。

### 面向内部的定位

`把模糊装修需求翻译成可执行设计输入`

这是产品的真实功能。系统真正做的事情，是把模糊、情绪化、场景化的表达，转换成结构化、可供设计继续使用的 artifacts。

### 面向投资人的定位

`让普通设计师拿到像设计总监整理过的需求包`

这是杠杆叙事。系统通过提升上游输入质量，提升整体设计质量与一致性。

## 3. 与长期愿景的关系

WowHome 的长期愿景，是成为家装行业的安卓层：把装修过程拆成标准化节点，每个节点都有明确的输入、输出、责任人、SLA 和验收标准。

但这个长期系统能成立，有一个前提：

`最前端的输入必须先被标准化。`

家装前链路最难的部分，不是“收集信息”，而是把人类高度模糊、情绪化、场景化的表达，翻译成后续参与者可以稳定消费的输入。

因此，当前 POC 不应该被当作：

- 一个完整家装平台
- 一个设计平台
- 一个交易平台
- 一个施工管理系统

它应该被理解为：

`WowHome 为后续全链路协作建立稳定输入协议的第一次验证。`

## 4. 核心假设

当前 POC 验证的核心假设是：

`一次高质量的 AI 引导式深度对话，可以生成一套双层 artifacts：既让用户感到被理解，也让设计师获得足够清晰的结构化输入，从而更快开始高质量工作。`

如果这个假设成立，WowHome 就验证了其操作系统的第一个真实原语。

如果这个假设不成立，那么后续节点化系统的基础输入将不稳定。

## 5. 优先级结构

当前阶段的验证优先级是：

### P0

- 需求标准化
- 设计能力放大

### P1

- 节点化协作是否成立

### P2

- 获客到交付的商业闭环是否成立

这个顺序非常重要。当前 POC **不需要**先证明完整商业模式是否成立，它首先要证明的是：

`平台能否稳定地产生更高质量的上游输入。`

## 6. POC 的范围边界

当前 POC 只验证这个最小闭环：

`用户进入 -> 深度对话 -> 用户层 artifacts -> 用户确认/补充 -> 设计师层 artifacts -> 设计师使用 -> 双方反馈`

当前 POC **不需要**包含：

- 自动匹配
- 支付或结算
- 施工流程
- 供应商比价
- 完整权限模型
- 产品内设计交付

这些内容都属于后续阶段。

## 7. 当前真正被验证的产品是什么

当前被验证的产品，本质上是一个：

**需求翻译引擎**

它在用户体验上应该包裹着具有情感共鸣的外壳，但底层真正完成的是“协议生成”。

它不应该被定义成：

- 一个问卷机器人
- 一个灵感板生成器
- 一个单纯的设计 Copilot
- 一个装修获客 CRM

它应该被定义成：

- 一个让用户感到被深刻理解的系统
- 一个把这种理解组织成可复用结构的系统
- 一个把这种结构翻译成设计可执行输入的系统

## 8. 双层 Artifacts

当前 POC 的核心输出是一套双层 artifacts。

### 第一层：面向用户的 artifacts

目的：

- 让用户感到被理解
- 反映其生活方式、优先级与情感诉求
- 帮助其更清楚地看到未来的家

可能包含的内容：

- 家庭与居住画像
- 生活模式摘要
- 未来生活场景
- 偏好地图
- 明确不喜欢和不可妥协项
- 优先级与取舍总结

成功标志：

用户会说出类似：

`对，这就是我们。`

### 第二层：面向设计师的 artifacts

目的：

- 把情绪与叙事翻译成设计语言
- 减少需求歧义
- 减少反复沟通和遗漏假设
- 让设计师基于更强的 brief 开始工作

可能包含的内容：

- 项目背景与硬约束
- 空间需求清单
- 用户优先级与冲突排序
- 风格锚点与避雷项
- 预算框架与弹性区间
- 风险点、未知项、后续待确认问题
- 推荐的设计切入方向

成功标志：

设计师会说出类似：

`这份材料让我更快开工，而且方向更清楚。`

## 9. 用户价值排序

用户侧的情感价值排序是：

1. **被理解**
2. **被启发**
3. **被梳理**

这意味着系统绝不能表现成一个冷冰冰的 intake 表单。

在体验上，它必须先建立认同感和信任感，之后才是结构化整理。结构要服务于情感对齐，而不是反过来。

## 10. 成功标准

### P0：用户侧成功

- 用户愿意完成一次深度对话
- 用户看到用户层 artifacts 后，明确觉得自己被准确理解
- 用户更倾向于确认或补充，而不是整体推翻输出

### P0：设计师侧成功

- 设计师能够基于设计师层 artifacts 开始工作
- 设计师反馈方向更清晰、遗漏需求更少
- 经验较少的设计师，借助这套 artifacts 也能做出更强的早期输出

### P1：协议层成功

- 两层 artifacts 之间存在稳定映射关系
- 重复项目中逐渐出现可复用的翻译结构
- 这套输出可以成为未来 WowHome 节点系统的标准起点

### P2：商业层成功

- 团队后续可以把这一层能力接入获客、转化和下游交付

## 11. 战略含义

如果 POC 成功，说明 WowHome 已经验证了其操作系统的第一个协议：

- 上游的人类模糊表达可以被规范化
- 这种规范化结构可以在角色之间流转
- 只要输入质量提升，设计质量就有机会被系统性放大

这将成为后续 `理 / 解 / 转 / 交` 节点化展开的基础。

如果 POC 失败，团队不应该急着推进下游协作，而应该先回头重新检查：

- 问题定义是否有误
- 对话流程是否不对
- artifacts 结构是否不成立
- 目标用户切口是否选错

## 12. 后续文档结构建议

后续 docs 建议演化为三层：

### Vision 层

回答：

- WowHome 为什么存在
- 为什么行业需要“安卓层”
- 它长期想成为怎样的基础设施

### Bridge 层

回答：

- 为什么当前 POC 是正确的第一步
- 当前 POC 在验证什么、不验证什么
- 当前 POC 如何连接到长期节点化系统

### Spec 层

回答：

- 当前 POC 具体做什么
- 边界和排除项是什么
- artifacts 结构是什么
- 验证指标是什么

这份文档属于 `Bridge` 层。

## 13. 本文档不定义什么

本文档不负责定义：

- 最终 UI 长什么样
- 精确对话流程怎么设计
- 详细技术架构
- 具体实施任务
- `解 / 转 / 交` 的后续路线图

这些内容应分别进入独立的 spec、research 和 planning 文档。

## 14. 结论

建议继续推进当前 POC，并明确将其定义为：

`一个以双层 artifacts 为核心输出的需求翻译引擎。`

解释规则如下：

- 对用户的承诺 = 理解
- 对内部的功能定义 = 翻译
- 对长期战略的角色 = 为未来操作系统生成协议
