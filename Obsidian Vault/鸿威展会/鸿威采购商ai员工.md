# 鸿威采购商控制系统的 AI 员工产品设计与落地报告

## 执行摘要

本报告聚焦在中国中小型展会场景下，如何用“AI 员工”把“采购商触达与需求控制”做成可复制、可规模化的系统能力：从线索获取、需求识别、触达对话、供需匹配、成交推进，到数据沉淀形成可复用的采购商资产与需求图谱。会展主办机构的数字化实践在复苏后进入“更重视盈利与效率”的阶段，且数字化人才缺口持续成为突出痛点，这为“用 AI 把运营能力产品化”提供了现实土壤。citeturn13search0turn13search19turn13search6

面向“采购商资源把控”这一核心诉求，本报告给出的可执行结论是：AI 员工不是一个“会说话的虚拟人”，而是一组可审计、可控、可迭代的专岗智能体（Agent），在组织与系统约束下自动执行标准化动作，并把每一次触达转成结构化“需求卡片”，从而形成跨展会复用的网络效应。具备“数字员工/智能伙伴常驻工作流、具备权限身份、可执行技能”的产品形态，已经在企业协同与客服领域形成成熟范式，可直接借鉴其“身份进入组织+技能编排+知识接入+持续运营”的实现路径。citeturn0search4turn0search5turn2search0

落地策略建议采用“三段式”：两周做出可用的半自动 MVP（先验证“能拿到有效需求”）；三个月实现可控的端到端闭环（可量化提升回复率/有效需求率/转化率，并显著降低人力触达成本）；一年进入平台化扩张（跨展会导流与需求复用、行业级知识与匹配资产沉淀）。为降低合规与生态风险，国内初期默认“数据与模型尽量留在境内”，并以《个人信息保护法》为核心建立“最小必要、明确告知、可撤回、可审计”的治理链路；如未来扩展海外触达与数据出境，则需按网信办的出境规则与标准合同机制规划可选路径。citeturn0search6turn1search0turn1search8turn1search2

## AI 员工产品全景与能力矩阵

### AI 员工产品的功能清单

AI 员工产品建议按“岗位”而非“功能点”来定义，以便组织协同、权限、KPI 与审计闭环。下面给出面向采购商控制的最小岗位集合（MVP 必选为前五类）。

- 虚拟 BD（Outbound SDR Agent）：找人、写信、发信、跟进、预约、生成需求卡、移交人工/供应商
- 自动客服（Inbound Service Agent）：对外应答、收集需求字段、FAQ/展会信息问答、分流到人工
- 需求识别器（Intent Miner）：从对话/表单/邮件中抽取需求要素（品类、规格、数量、交期、预算、交付地、资质），并做意向分层
- 匹配引擎（Match Engine）：把需求卡与展商/供应商库匹配，给出 Top-N 推荐与理由、风险提示
- 跟进机器人（Nurture & Follow-up Bot）：多轮触达、异议处理、沉默唤醒、会议提醒、资料补齐
- 成交推进助手（Deal Copilot，可选）：报价要点、条款清单、催推进度、会议纪要、下一步行动建议
- 数据管家（Data Steward，可选）：去重合并、标签体系、字段完整度、数据质量评分、合规校验

企业级“智能体平台/数字员工”通常强调：知识接入、技能编排、效果调优与持续运营；并能以“联系人/员工身份”常驻在工作流中，这种平台形态可作为你们自研的参照系或替代实现路径之一。citeturn0search5turn0search4turn2search0

## 模块级技术实现方案

本节按产品模块给出：模型类型、数据源、接口/集成点、自动化流程与关键工程要点。模型选型建议优先国内可用、接口稳定且支持工具调用/JSON 输出的方案；例如 DeepSeek 提供 OpenAI 兼容接口与工具调用能力，并公布了 token 计费规则，可便于你们做成本建模。citeturn3search0turn9view0

### 虚拟 BD

**要解决的问题**：把“600 人团队/全网营销/大量触达”的愿景，压缩为“少量运营 + AI 自动化”，且可控、可审计、可迭代。

**模型类型**
- 生成与多轮对话：通用大语言模型（LLM），要求支持工具调用与结构化输出（JSON）。citeturn9view0turn11search31turn11search11  
- 线索评分：可先用规则+轻量 ML（Logistic/GBDT），三个月后再引入“基于对话与行为的学习排序（LTR）”。

**数据源**
- 线索来源（MVP）：主办方已有观众/采购商登记、历史名片/表单、合作协会名单（手工导入 CSV 即可）。  
- 线索来源（可选扩展）：公开网站、行业名录、社媒账号等（需合规评估与最小化采集）。citeturn0search6  
- 业务知识：展会信息、品类目录、展商清单、历届采购需求（用于个性化与问答）。citeturn13search6turn13search16

**接口与集成**
- 触达通道：企业微信/邮件/表单。企业微信“客户联系”相关能力（客户详情、客户群列表、企业群发等）在生态中普遍通过 API/第三方平台接入，便于自动化；同时存在“新客户欢迎语 welcome_code”等事件型接口，适合做“加好友后首触达”自动化。citeturn8search10turn8search8turn1search3turn14search0  
- 日程：钉钉/飞书/腾讯会议/邮箱日历（MVP 可先人工确认，避免过早集成）。

**自动化流程（建议先半自动）**
1. **导入线索** → 去重（公司+手机号/邮箱哈希）→ 分层（国家/行业/角色）。  
2. **生成首触达**：LLM 读取“展会与品类摘要 + 对方行业画像”生成 1 条短消息（≤400 字），并产出 JSON：`{value_prop, ask, CTA, compliance_line}`。  
3. **人审后发送**（两周 MVP 强烈建议）：运营人员点选“通过/改写/不发”。  
4. **回复分类**：需求识别器判定 {强意向/弱意向/不相关/拒绝/需转人工} 并生成下一步追问。  
5. **预约或生成需求卡**：强意向→补齐字段→在 CRM 生成“需求卡片（Demand Card）”并进入匹配。

**工程关键点**
- “多轮序列”必须有频控与停机条件（退订/拒绝/无关即停止），否则容易触发渠道风控与投诉风险。citeturn0search6  
- 每次发送都要落审计日志（发给谁、内容、时间、模板版本、批准人/自动规则）。

### 自动客服

**要解决的问题**：让采购商“随时能问、能得到靠谱答复、能被引导到留下需求”，同时减少人工重复答疑。

**模型类型**
- RAG 问答：LLM + 检索增强生成（向量检索+引用片段）。向量库可用 Milvus 或 pgvector 模式快速搭建。citeturn3search2turn11search10  
- 结构化表单机器人：LLM 负责对话与追问；字段校验由规则引擎/正则/字典完成。

**数据源**
- 展会 FAQ、时间地点、参观/报名规则、品类范围、参展商名录、交通与酒店建议等（从主办方资料汇总到知识库）。  
- 历史客服对话与工单（用于补齐知识与训练意图）。客服平台通常强调“机器人+人工+工单”的一体化，这类系统形态可借鉴其知识运营方法。citeturn5search0turn5search8turn12search0

**接口与集成**
- 官网/小程序 IM、企微对话、公众号渠道等（先选一个渠道做深做透）。  
- 工单系统：统一把“问答未解决/高价值需求”转为工单，保证 SLA。

**自动化流程**
1. 进入对话 → 意图识别（问答 vs 留资 vs 报名咨询）。  
2. 问答走 RAG，答案返回同时附“下一步 CTA”（如：填写需求表单/加企微/预约对接）。  
3. 需要留资时：按字段追问并校验，生成需求卡。  
4. 置信度低或敏感问题：转人工并带上上下文摘要。

**工程关键点**
- 知识库要“可运营”：按未命中问题自动生成“待补充知识”列表；类似 Zendesk 等平台强调以 persona、知识源、用例/流程（procedures/dialogues）来控制生成式答案的稳定性，这类方法论可迁移到你们系统中。citeturn12search5turn12search17  

### 需求识别器

**要解决的问题**：把“客户说了什么”压成“可匹配、可统计、可复用”的结构化需求资产，是采购商控制系统的数据发动机。

**模型类型**
- 信息抽取：LLM（JSON 输出）+ 规则校验；并行引入轻量 NER/Regex 作为兜底。  
- 相似需求聚类：Embedding + 聚类（HDBSCAN/KMeans）用于“同类需求合并/复用”。

**数据源**
- 对话文本（企微/邮件/IM）、表单字段、附件（如采购清单 PDF，可选 OCR/解析）。  
- 供应商品类本体（类目树、规格字典）。

**接口与集成**
- 输入：`/messages/ingest`（对话片段、渠道、会话 ID、联系人 ID）  
- 输出：`/demand_cards/create`（结构化需求卡）

**需求卡（建议字段）**
- 基本：品类、用途场景、规格/认证、数量区间、预算区间、交付地、交期、决策角色、采购阶段  
- 触发来源：展会/渠道/活动/关键词  
- 风险：字段缺失、冲突、疑似不真实、合规状态（同意/退订）

### 匹配引擎

**要解决的问题**：让需求能被快速路由到“最可能成交”的展商/供应商，并沉淀“为什么匹配”的可解释理由，支撑后续网络效应。

**模型类型**
- 第一阶段（MVP）：规则过滤（品类、产地、资质、MOQ、交付）+ 向量相似度 Top-N。  
- 第二阶段（三个月）：加 reranker（交叉编码器）做重排，提升 Top-3 准确率。Embedding 可采用 BGE 系列多语种模型，具备面向检索的多功能性与多语种能力，适合你们未来扩展海外采购信息。citeturn11search0turn11search24  
- 一年：学习排序（LTR），用真实成交/推进结果做监督信号，形成闭环。

**数据源**
- 供应商库：公司画像、产品目录、价格带、交付能力、资质、历史成交与反馈。  
- “成功样本”：成交/有效对接的需求-供应对（对 LTR 很关键）。

**接口与集成**
- `POST /match`：输入 demand_card_id，输出 `[{supplier_id, score, reasons, missing, risk_flags}]`  
- `POST /introductions`：生成对接材料（双方一页纸）、引导建群/约会

**自动化流程**
1. 需求卡入库 → 类目映射（本体）→ 规则过滤掉不满足硬条件的供应商。  
2. 对剩余候选做向量召回（Top 50）→ reranker 重排（Top 10）→ 输出 Top 3–5。  
3. 生成“对接包”：双方简介、需求摘要、建议下一步问题清单（人工可编辑）。  
4. 把结果回写 CRM，并设置“推进任务”。

### 跟进机器人

**要解决的问题**：决定“回复率→有效需求率→转化率”的不是第一条消息，而是“稳定、克制、可控”的多轮跟进策略。

**模型类型**
- 规则驱动的有限状态机（FSM）+ LLM 生成（每个状态只允许有限动作）  
- 关键点在“策略与约束”而非更大模型

**数据源**
- 触达策略库（不同展会/品类/国家模板）  
- 对话历史与偏好（但必须合规可撤回）citeturn0search6  

**接口与集成**
- 触达通道 API  
- 任务系统（提醒人工介入）

**自动化流程（典型状态机）**
- `new_lead → contacted → replied_positive → qualified → matched → intro_sent → meeting_scheduled/closed`

## 关键 KPI 与量化目标

下列 KPI 建议按“漏斗 + 成本 + 自动化率”三类管理，并以两周/三个月/一年分别设目标。目标值应由你们选定行业、线索质量与触达渠道决定，本报告给出可执行的“目标框架 + 建议起始值”，便于产品与运营对齐。

### 漏斗类 KPI

- **投递成功率**（Delivery Rate）：成功送达 / 总发送  
- **回复率**（Reply Rate）：有任何回复 / 成功送达  
- **有效需求率**（Qualified Demand Rate）：产出合格需求卡 / 有回复  
- **预约率**（Meeting Rate）：预约成功 / 合格需求卡  
- **对接转化率**（Intro-to-Deal Rate）：进入实质对接或产生商机 / 预约  
- **成交率**（可选，周期更长）：成交 / 商机

建议目标（可根据你们历史数据调参）：
- 两周 MVP：回复率 ≥ 3%，有效需求率（以需求卡口径）≥ 25%，预约率 ≥ 20%  
- 三个月：回复率 ≥ 5–8%，有效需求率 ≥ 30–40%，预约率 ≥ 25–35%  
- 一年：形成跨展会复用后，用“复用带来的新增有效需求占比”作为关键北极星之一

### 成本与效率 KPI

- **单条有效需求成本**（Cost per Qualified Demand）：（人力 + 模型 + 云资源 + 通道）/ 合格需求卡数  
- **人均周触达量**：每个运营/BD 每周可覆盖的有效触达数  
- **自动化率**：AI 自动完成的步骤数 / 全流程步骤数（或自动处理的会话占比）

大模型成本可以用公开 token 计费直接建模。例如 DeepSeek 给出输入/输出单价，并区分 cache hit/miss；你们可按“每条线索平均消耗 tokens × 单价”估算边际成本，再与人工成本对比，明确“AI 员工能否三人顶三十人”的财务边界。citeturn9view0

## 合规与隐私风险、可复用组件与竞品对比

### 合规与隐私风险与缓解措施

以《个人信息保护法》为核心，你们在“采购商线索→触达→沉淀画像”链路中至少要处理个人信息（姓名、联系方式、沟通记录等），因此需要把“目的限定、最小必要、公开透明、可撤回、可审计”做成产品默认能力，而不是后置补丁。citeturn0search6turn0search0

关键风险与缓解建议如下（强调可执行）：

1) **线索来源合法性与告知**  
- 风险：从公开渠道抓取/购买名单，缺乏明确告知与授权，容易触发投诉与监管风险。  
- 缓解：优先使用“展会报名/观众登记/用户主动留资”作为主数据源；对任何外部数据源建立“来源字段 + 合规状态字段”；触达首条消息加入清晰的退订/拒收方式。citeturn0search6  

2) **对话存档与监控**  
- 风险：会话存档属于高敏感运营能力，可能涉及员工与外部个人信息。  
- 缓解：在系统中实现“存档范围、用途、保留期、访问控制、审计”的管理；默认只对“业务必要字段”做结构化抽取，原文分级存储与严格权限。citeturn1search0turn1search8  

3) **自动化决策与歧视风险**  
- 风险：用 AI 给采购商打分、自动拒绝或差异化对待，可能引发争议。  
- 缓解：评分模型输出必须可解释（贡献因子/规则命中）；关键决策（拉黑、拒绝、出境传输）强制人工确认；建立申诉/纠错入口。citeturn0search6  

4) **数据安全与分级分类**  
- 风险：需求卡与画像属于高价值数据资产，一旦泄露影响巨大。  
- 缓解：按《数据安全法》建立数据分类分级、最小权限、加密与脱敏、访问审计、风险评估与应急预案。citeturn1search0turn1search8  

5) **未来海外扩展的数据出境**（可选）  
- 风险：若模型/CRM/触达系统在境外，可能触及个人信息出境要求。  
- 缓解：优先选择境内部署与境内模型；确需出境时，评估是否适用标准合同路径并履行备案等要求。citeturn1search2turn1search12

### 示例对话与触达脚本（可直接用于 MVP）

以下脚本以“中小型展会采购商”为目标，默认渠道为邮件/企微均可（按你们实际渠道改称谓）。每条消息都内置“退出机制”，以降低投诉风险并便于合规审计。citeturn0search6

**虚拟 BD：首触达（短版，≤120 字）**  
> 你好，我是【鸿威展会】采购对接助理。看到你们在【品类】有采购/选品需求，我们可把本届展会内合适的工厂/品牌按你的规格做一份 5 家清单（含资质与参考价）。如果你愿意，我只问 3 个问题：品类/数量区间/交付地？不方便也可回复“停止”，我将不再联系。

**虚拟 BD：跟进（对方未回复，T+2 天）**  
> 补充一句：我们不是群发广告，会按你的条件做匹配清单。若本期不需要，回“停止”即可；如需要，回“1”我发 3 个问题给你，2 分钟搞定。

**需求识别器：强意向后的字段追问（结构化）**  
> 为了把清单做准，我还缺两项：  
> 1）是否需要【认证/材质/规格】？
