# VirtuForge 1.1 三方视角评审意见

---

## Agent 1：OPC客户视角（一人公司老板）

**角色背景：** 做外贸的，一个人跑业务、管财务、盯供应链，每天12小时。

**意见：**

**1. 入口逻辑不对，应该先问诊再选岗**
进来第一眼看到13个岗位，不知道从哪里下手。真实问题是"我现在最痛的事是什么"，不是"我要选哪个岗位"。建议加一个问诊入口：3个问题问我现在最头疼什么，然后推荐应该先做哪个虚拟员工。

**2. 价格区间没有说服力，缺少ROI描述**
¥2万-¥6万对OPC是一笔大钱，但不知道花出去之后能得到什么。"虚拟员工实例"、"管理后台"这些词没有意义。需要用业务语言说：这个员工上线后，每周能省几个小时，能帮多跟进几个客户。

**3. 工程拆解页面（Step 3）对OPC完全不可读**
"多轮对话状态机"、"Webhook回调处理"——不知道这些是什么，也不知道该不该勾选。这一步要么对OPC用户隐藏，要么翻译成业务价值描述。

**4. 流程走完没有成交动作**
整个流程结束后没有留下联系方式，也没有人说下一步怎么办。这是一个演示，不是一个能成交的产品。需要在交付页加入"预约顾问"或"提交需求"的出口。

## Agent 2：人社厅补贴官员视角

**角色背景：** 负责中小企业数字化转型补贴审核，每年审几百个项目，要对上级负责，要防止骗补。

**意见：**

**1. 补贴计算逻辑在政策上站不住脚**
直接按总成本×30%，没有上限、没有分档、没有资质门槛。真实补贴政策必须有：单个企业补贴上限（如不超过10万）、企业规模分档（小微/小型/中型）、项目类型分类（首次数字化/升级改造）。

**2. "已交付"状态缺乏第三方验收机制**
系统自动打的状态，无法作为补贴依据。补贴审核需要：第三方验收报告、企业使用证明（如系统登录日志）、发票和合同。当前"政府监管视角"只是一张漂亮的表格，不是真正的审计链。

**3. 复杂度评分是硬编码，无法解释**
代码里写死了 `overall: 72`，不是基于用户输入计算的。如果这个数字要作为补贴依据，必须有可重现的计算过程，否则一旦被审计，无法解释为什么是72分而不是50分。

**4. 缺少企业主体信息，补贴无法发放**
补贴要打给谁？整个流程没有收集：企业名称、统一社会信用代码、银行账户、法人信息。这些是补贴发放的前提条件。

**5. 页面命名有问题**
"政府监管视角"这个名字本身有问题。这应该叫"补贴申请材料"或"项目备案信息"，监管是政府的动作，不是企业自己贴的标签。

## Agent 3：开发者视角

**角色背景：** 接到这份需求，要把它从演示变成真正可用的产品。

**核心判断：当前是一个线性演示流程，不是一个真正的业务系统。**

### 技术债务

**1. 复杂度评估是硬编码（最大虚假点）**
`app.js:195-211`，所有用户得到的都是同一份评估结果（overall: 72, minCost: 20000等）。要真正上线，这里必须接真实的AI API，或者至少基于用户输入做规则计算。

**2. 状态管理结构脆弱**
所有状态在顶层App组件用`useState`平铺，13个状态变量现在还能管，但一旦加入用户账户、历史记录、多项目管理，这个结构会崩。扩展前需要引入`useReducer`或轻量状态管理。

**3. 业务数据硬编码在前端**
`VIRTUAL_EMPLOYEES`和`ENGINEERING_MODULES`全部写死在前端。改一个岗位的价格要重新部署。这些数据应该从后端接口拉取，或者至少放在独立的配置文件里。

### 功能缺口（按优先级）

| 优先级 | 功能 | 说明 |
|--------|------|------|
| P0 | 用户身份系统 | 没有登录，没有保存，刷新全没了。localStorage只保存了idea文本，不够 |
| P1 | 真实AI评估接入 | 把`setTimeout`模拟替换成真实的Claude API调用，基于用户8维输入生成真正的复杂度分析 |
| P2 | 补贴申请表单 | 在政府监管页面加入企业信息收集和PDF导出，这样这个页面才有实际价值 |
| P3 | 工程拆解页面UX重做 | 对OPC用户隐藏技术术语，改成业务价值描述 |

### 架构决策（需在动手前确认）

当前是纯前端单页应用，没有后端。如果要做补贴申请、用户账户、真实AI评估，需要加一个轻量后端（Node/Python均可）。这个决策影响整个部署方式，必须在开始开发前确认。
