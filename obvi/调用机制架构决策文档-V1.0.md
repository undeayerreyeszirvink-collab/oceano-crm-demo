## 1. 执行摘要

本文档基于《企业级虚拟劳动力管理平台》PRD V1.1 和系统架构设计文档 V1.0，针对平台四大核心组件（Ontology、Skills、Orchestration、CLI Gateway）的调用机制进行系统性评估，明确各组件应采用的技术实现路径。

### 1.1 问题背景

当前 AI Agent 生态中，存在多种赋予 Agent 能力的技术路径，包括但不限于：

- **Agent Skills 开放标准**（agentskills.io）：以 SKILL.md 为核心的文件夹式知识/流程封装
- **MCP（Model Context Protocol）**：标准化的跨平台工具访问协议
- **编排框架原生 Tool/Function**：各编排引擎（**OpenClaw**、LangGraph、ADK、AutoGen 等）自带的工具调用机制
- **Graph RAG**：知识图谱增强的检索生成

本平台的四大组件虽在 PRD 中统一称为"Skills"和"CLI"，但它们在语义本质上存在根本性差异，**不应使用同一种调用机制处理**。

### 1.2 核心决策

经过对产品需求、安全要求、性能指标和生态兼容性的综合评估，我们识别出平台中存在三种本质不同的调用模式：

| 调用模式 | 适用组件 | 推荐机制 | 关键依据 |
|----------|----------|----------|----------|
| **知识注入** | Ontology 查询策略 | Agent Skills 格式 + Graph RAG | "认知"而非"动作"，适合渐进式加载 |
| **能力执行** | L1/L2/L3 Skills 体系 | 双层模型：Skills 格式定义 + 编排引擎原生 Tool 运行时 | 兼顾可移植性与类型安全 |
| **系统操作** | CLI Gateway 命令 | 自研 CLI Gateway + 编排引擎 Tool Call | 安全模型远超 MCP 能力范围 |

> **关键原则：V1.0 阶段不引入 MCP**
>
> MCP 的核心价值是"标准化跨平台工具访问"，但本平台 V1.0 聚焦企业微信单一渠道，Agent 仅通过自研编排引擎调用 CLI，不存在跨平台工具共享需求。企业级安全要求（动态 Token、PDP 策略决策、幂等控制、不可篡改审计）远超 MCP 的安全模型。建议在 V2.0 扩展飞书/钉钉等多 IM 平台时，评估 MCP 作为外部系统集成协议的价值。

## 2. 调用类型分类学

本章对平台内所有"调用"行为进行分类，建立统一的概念框架。

### 2.1 三种调用的本质差异

#### 2.1.1 类型 A：知识注入（Knowledge Injection）

**适用组件：** Ontology（企业业务本体模型）

Ontology 是 Agent 的"世界观"——它不是一个被调用的工具，而是 Agent 推理时的**上下文约束**。编排引擎通过查询 Ontology 来验证执行路径的合规性（FR-004 AC-002），理解业务概念间的关联关系。

**语义特征：** Agent 需要"理解"而非"执行"。Ontology 提供的是认知基础，不是操作指令。

#### 2.1.2 类型 B：能力执行（Capability Execution）

**适用组件：** 三级 Skills 体系（L1 通用 / L2 行业 / L3 私有）

Skills 在架构文档中被定义为具有 `executor_type`（llm / rule / hybrid）、`input_params`、`output_schema`、`cli_dependencies` 的结构化执行单元。例如"报销流程处理"技能有明确的输入参数（报销类型、金额）、输出结构（expense_id、status、approval_route）以及对 CLI 命令的依赖链。

**语义特征：** 这是可执行的能力模块，本质上是编排引擎的 Tool/Function，但需要版本控制、依赖管理和跨模型可移植性。

#### 2.1.3 类型 C：系统操作（System Operation）

**适用组件：** CLI Gateway（受控的系统交互通道）

CLI 是具有动态 Token 授权（5 分钟有效期、一次性使用、参数绑定防篡改）、策略决策点（PDP/PIP）、幂等控制、熔断降级和不可篡改审计日志的受控操作通道。每次操作都需要编排引擎向 Token 服务申请短期 Operation Token，经过策略检查后方可执行。

**语义特征：** 这是最严格的"动作"调用，安全约束是第一优先级，需要全链路可审计。

### 2.2 分类决策矩阵

| 判断维度 | 类型 A 知识注入 | 类型 B 能力执行 | 类型 C 系统操作 |
|----------|----------------|----------------|----------------|
| 是否改变外部状态 | 否 | 可能（通过 CLI 依赖） | 是 |
| 是否需要实时响应 | 中（可缓存） | 高（P95 < 3s） | 高（P95 < 3s） |
| 是否需要权限控制 | 租户隔离即可 | 技能级权限 | 操作级动态 Token |
| 是否需要审计日志 | 低优先级 | 中优先级 | 强制（不可篡改） |
| 是否需要版本控制 | 图谱快照 | 完整版本链 | 命令定义版本 |
| 调用频率 | 每次推理 | 每次任务 1-3 个 | 每次任务 1-5 个 |
| 加载策略 | 预加载 + 查询 | 渐进式按需加载 | 即时调用 |

## 3. Ontology 调用机制设计

### 3.1 推荐方案：Graph RAG + Agent Skills 查询策略

Ontology 的核心使用方式是为 Agent 提供业务知识上下文，而非执行操作。因此推荐采用 **Graph RAG**（知识图谱增强检索生成）作为运行时检索引擎，同时用 **Agent Skills 格式**管理不同场景的查询策略。

具体的 Graph RAG 实现方案（如 LlamaIndex KnowledgeGraphIndex、LangChain GraphRAGRetriever、或自研检索链路）由技术选型阶段确定，本文档仅约束调用语义。

#### 3.1.1 查询策略的 Skills 化管理

将 Ontology 的不同使用场景封装为独立的 Agent Skills，编排引擎在不同阶段按需加载对应策略：

```
ontology-skills/
├── compliance-check/
│   └── SKILL.md              # 合规性校验：验证操作路径是否符合企业规则
│   └── references/
│       └── rule-patterns.md  # 常用合规规则查询模式
├── entity-lookup/
│   └── SKILL.md              # 实体查询：理解业务概念、消歧、关联发现
│   └── references/
│       └── query-templates.md # 图查询模板（Cypher/SPARQL/Gremlin 等）
├── relationship-trace/
│   └── SKILL.md              # 关系追踪：审批链路、组织架构、成本归属
└── context-enrichment/
    └── SKILL.md              # 上下文增强：为任务规划注入业务背景
```

#### 3.1.2 运行时调用流程

| 阶段 | 触发条件 | 加载的 Ontology Skill | 输出 |
|------|----------|----------------------|------|
| 任务规划 | 编排引擎接收用户指令 | context-enrichment | 注入业务上下文到规划 Prompt |
| 路径校验 | 执行路径生成后 | compliance-check | 合规/违规标记 + 修正建议 |
| 实体消歧 | 指令中存在歧义实体 | entity-lookup | 候选实体列表供用户选择 |
| 审批路由 | 触发 Human-in-the-Loop | relationship-trace | 审批人链路和授权范围 |

> **设计原则：Ontology 查询不是 Tool Call**
>
> Ontology 查询结果应直接注入 Agent 的推理上下文（System Prompt 或 Context Window），而不是作为 Tool Call 的返回值。这确保 Agent 在整个推理过程中持续感知业务约束，而非仅在"调用 Ontology 工具"时才考虑业务规则。
>
> 无论最终选用何种 Graph RAG 实现，都应遵循这一"上下文注入"而非"工具调用"的语义原则。

## 4. 三级 Skills 调用机制设计

### 4.1 核心架构：双层模型

三级 Skills 体系采用"双层模型"——Agent Skills 标准格式用于定义和管理，编排引擎原生 Tool 用于运行时执行。**这是本文档最重要的架构决策。**

```
┌─────────────────────────────────┐    ┌─────────────────────────────────┐
│      编写/管理层（给人看的）       │    │      运行时层（给 Agent 用的）     │
│                                 │    │                                 │
│  SKILL.md  (Agent Skills 标准)   │    │  SkillDefinition (Pydantic)     │
│  ├── references/               │    │  ├── executor_type              │
│  ├── scripts/                  │ ──►│  ├── input_params / output      │
│  └── assets/                   │编译 │  ├── cli_dependencies           │
│                                 │    │  └── prompt_template            │
│  版本控制 / 业务可编辑 / 可移植    │    │  注册数据库 / 编排引擎原生 Tool    │
└─────────────────────────────────┘    └─────────────────────────────────┘
```

**为什么不直接用 Agent Skills 标准格式运行？**

Agent Skills 标准格式的渐进式加载（Metadata → Instructions → Resources）非常适合"发现"和"管理"技能，但它缺乏运行时所需的：

- **类型安全**：input_params / output_schema 需要 Pydantic 级别的校验
- **依赖解析**：技能间的前置依赖和 CLI 命令依赖需要递归解析
- **执行策略**：executor_type（llm / rule / hybrid）决定执行路径
- **版本锁定**：同一技能的不同版本可能同时服务于不同 Agent 实例

因此我们需要一个"编译"步骤，将声明式的 SKILL.md 转换为可执行的 SkillDefinition 对象。

### 4.2 L1 通用技能：编排引擎原生预加载节点

**调用方式：** 直接内置于编排引擎的执行图节点函数，不使用渐进式加载。

**理由：** L1 技能（意图识别、文本总结、基础问答、数据提取）是 Agent 的基础能力，每次任务必定使用。渐进式加载会引入不必要的延迟，违反 NFR-002 的 P95 < 3s 响应要求。

| L1 技能 | 实现方式 | 加载策略 | 性能要求 |
|---------|----------|----------|----------|
| 意图识别 | 编排引擎入口节点 + LLM 分类 | Agent 初始化时预加载 | < 500ms |
| 文本总结 | LLM Chain + 长文本分块策略 | Agent 初始化时预加载 | < 2s |
| 基础问答 | Graph RAG + Ontology 上下文 | Agent 初始化时预加载 | < 1.5s |
| 数据提取 | 结构化输出 Parser + Schema 校验 | Agent 初始化时预加载 | < 1s |

### 4.3 L2 行业技能：Skills 格式定义 + 编译注册

**调用方式：** 以 Agent Skills 标准格式编写和分发行业技能包，系统导入时编译为 SkillDefinition 注册到技能注册表（数据库），运行时由 SkillLoader 按需加载为编排引擎 Tool。

L2 技能包示例结构（财务行业包）：

```
finance-skills-pack/
├── double-entry-booking/
│   ├── SKILL.md                      # 技能描述、使用时机、执行步骤
│   │   frontmatter:
│   │     name: double-entry-booking
│   │     description: 复式记账法验证与分录生成...
│   │     metadata:
│   │       level: L2
│   │       industry: finance
│   │       version: "2.1.0"
│   ├── references/
│   │   ├── accounting-standards.md    # 会计准则参考
│   │   └── entry-patterns.md         # 常见分录模式
│   ├── scripts/
│   │   └── validate_balance.py       # 借贷平衡校验脚本
│   └── assets/
│       └── chart-of-accounts.json    # 科目表模板
├── invoice-recognition/
│   ├── SKILL.md
│   └── ...
└── manifest.yaml                     # 技能包清单与依赖声明
```

#### 4.3.1 编译流程

| 步骤 | 操作 | 输入 | 输出 |
|------|------|------|------|
| 1. 解析 | 解析 SKILL.md frontmatter + body | SKILL.md 文件 | name / description / metadata |
| 2. 推断 | 从指令体中提取参数和输出结构 | Markdown body + references/ | input_params / output_schema |
| 3. 绑定 | 关联 CLI 命令依赖 | 指令中的 CLI 引用 | cli_dependencies 列表 |
| 4. 注册 | 写入 skill_versions 表 | SkillDefinition 对象 | skill_id + version 记录 |
| 5. 缓存 | 预热缓存 | 活跃版本 | 缓存条目 |

### 4.4 L3 企业私有技能：最核心的 Skills 应用场景

> **L3 是产品护城河（PRD 9.2 节"资产可沉淀"）**
>
> L3 私有技能是企业从 Ontology 中提炼出的独有 SOP，是平台"资产可沉淀"战略的核心载体。采用 Agent Skills 标准格式存储，确保：
>
> 1. **跨模型可移植** — 未来更换 LLM 时技能资产原封保留，仅需重新编译
> 2. **业务可编辑** — 管理员可通过 Markdown 编辑技能内容，无需编程
> 3. **渐进式加载** — L3 数量可能很大（每租户数十个），但每次任务仅激活 1-2 个

**调用方式：** 岗位定义（FR-006）阶段由系统从上传文档中自动提炼 L3 技能候选列表，输出为 SKILL.md 格式；管理员确认/调整后，系统编译为 SkillDefinition 并注册。运行时按需加载。

#### 4.4.1 L3 技能自动提炼流程

```
企业文档上传 ──► Ontology 引擎解析 ──► 实体-关系图谱
                                          │
                                          ▼
                                  LLM 提炼 SOP 流程
                                          │
                                          ▼
                                  生成 SKILL.md 草稿
                                          │
                                          ▼
                               管理员审核/编辑 SKILL.md
                                          │
                                          ▼
                          编译为 SkillDefinition + 注册入库
```

#### 4.4.2 L3 技能 SKILL.md 示例

以下为系统自动生成的 L3 技能文件示例（经管理员确认后的最终版本）：

```yaml
---
name: expense-reimbursement-process
description: |
  处理企业内部报销申请流程，包括费用核对、规则验证、审批路由。
  当用户提及报销、费用核对、报销审批时激活此技能。
metadata:
  level: L3
  tenant_id: tenant_001
  version: "1.0.0"
  source_ontology: ontology_finance_v3
  auto_generated: true
  confirmed_by: admin@company.com
  confirmed_at: 2026-04-15
---

# 报销流程处理技能

## 执行步骤

1. 解析用户的报销请求，提取：报销类型、金额、日期、事由
2. 查询 Ontology 确认费用归属的成本中心
3. 调用 CLI 命令 `erp.expense.query` 核对费用明细
4. 验证是否符合公司报销规则（参见 references/expense-rules.md）
5. 如金额超过 1000 元，触发 Human-in-the-Loop 审批
6. 审批通过后调用 `erp.expense.submit` 提交报销单

## 约束条件

- 单笔报销金额上限 100,000 元
- 招待费报销需附带参会人员名单
- 差旅费需与考勤记录交叉验证
```

### 4.6 L1-L3 Skills 分层判定标准

为保证 Skills 体系在规模扩展后仍具备可复用性、可维护性和可编排性，平台对 `L1 / L2 / L3` 采用统一分层标准。该标准不以“能力复杂度”作为划分依据，而以“复用边界、语义依赖和流程主权”作为核心判定维度。

`L1 Skills` 定义为不带企业私有语义的基础原子能力，主要承担意图识别、信息抽取、文本总结、结构化转换、澄清追问等基础认知与处理功能。L1 的目标是为所有业务场景提供稳定、低耦合的共性能力，其设计应避免耦合行业规则、企业制度和审批链。

`L2 Skills` 定义为带有行业语义、可在同行业企业间复用的业务能力模块。L2 通常依赖行业 Ontology 和行业知识规则，例如财务场景中的费用分类、发票识别、预算校验，采购场景中的库存判断、供应商匹配、比价评估。L2 的职责是提供行业级能力沉淀，而非承载某一企业的专属流程。

`L3 Skills` 定义为绑定企业 Ontology、岗位职责、审批关系和例外规则的专属流程能力。L3 承载企业独有的 SOP，是平台“资产可沉淀”战略的核心载体。L3 通常通过编排多个 L2 与 L1 Skill 实现完整业务闭环，并在必要时挂接 CLI Gateway 与 Human-in-the-Loop 节点。

平台对 Skill 的分层采用如下判定原则：若某项能力可跨行业、跨企业复用，则优先归入 L1；若其依赖明确行业语义、但在同行业企业之间仍具备较高复用性，则归入 L2；若其强依赖单一企业的制度、岗位权限、审批链或例外处理逻辑，则归入 L3。对于表达完整业务闭环的 Skill，应优先视为 L3；对于仅承担识别、抽取、转换等原子处理功能的 Skill，应优先视为 L1。

为防止分层漂移，平台要求所有 Skill Candidate 在注册前强制补齐以下元数据：`candidate_level`、`domain`、`scope`、`tenant_specific`、`depends_on_ontology`、`depends_on_cli`、`human_in_the_loop`、`reuse_scope`。其中 `scope=atomic` 通常对应 L1，`scope=module` 通常对应 L2，`scope=workflow` 通常对应 L3。

该分层标准的直接收益在于：一方面能够确保 L1 的稳定性与平台级复用能力，另一方面能够将行业通用能力沉淀于 L2，并将企业差异化资产集中沉淀于 L3，从而避免“所有 Skill 都长成大而全流程”的设计失控问题。

#### 4.6.1 L1-L3 分层判定矩阵

| 判定维度 | L1 通用原子能力 | L2 行业能力模块 | L3 企业专属流程能力 |
|----------|------------------|------------------|----------------------|
| 复用边界 | 跨行业、跨企业 | 同行业跨企业 | 单企业 / 单租户 |
| 语义依赖 | 不带企业私有语义 | 带行业语义 | 强依赖企业 Ontology |
| 典型粒度 | 原子步骤 | 业务模块 | 业务闭环流程 |
| 对审批链依赖 | 无 | 可输出建议 | 强依赖 |
| 对 CLI 依赖 | 原则上不直接调用 | 可少量查询 | 常通过 CLI 落地 |
| Human-in-the-Loop | 不包含 | 可提示 | 常包含 interrupt / resume |
| 维护主体 | 平台团队 | 行业方案团队 | 实施团队 / 企业管理员 |
| 典型示例 | 意图识别、字段抽取、摘要 | 发票识别、预算校验、供应商匹配 | 报销流程、折扣特批、紧急采购 |

#### 4.6.2 快速判定规则

| 判定问题 | 判定结论 |
|----------|----------|
| 换一个行业还能直接复用吗？ | 是：优先归入 L1 |
| 换一家同行业公司还能大体复用吗？ | 是：优先归入 L2 |
| 是否强依赖企业自己的 SOP、岗位权限、审批链、例外规则？ | 是：归入 L3 |
| 是否表达完整业务流程而非单点能力？ | 是：优先视为 L3 |
| 是否仅承担识别、抽取、转换等原子功能？ | 是：优先视为 L1 |

### 4.7 从 SOP 自动提取 Skill 的规范流程

平台在岗位定义、行业包构建和企业私有能力沉淀过程中，不直接将原始 SOP 或操作文档整体转换为 Skill，而采用“先 Ontology、后 Skill；先拆解、后编译”的规范流程。该流程旨在保证能力边界清晰、依赖显式、运行时可编排。

第一阶段为文档预处理。系统对上传的 SOP、制度、操作手册、培训资料及样例表单进行统一清洗，去除噪声内容，并按标题、步骤、表格、规则说明、例外条款等结构切分为可解析文本块。同时，系统为每个文本块打上类型标签，如定义、规则、步骤、角色、系统动作、审批条件、例外处理等，为后续抽取提供基础。

第二阶段为 Ontology 提取。平台首先从文档与结构化数据中抽取业务世界模型，而非直接生成 Skill。必须抽取的 Ontology 元素包括：实体、角色、关系、状态、规则、事件以及决策点。例如在采购场景中，需要明确“采购申请”“供应商”“预算”“审批人”等实体，以及“部门拥有预算”“库存不足方可采购”“超预算需审批”等关系与规则。该阶段的目标是形成稳定的业务语义基础，使后续 Skill 的边界判定有统一参照。

第三阶段为 SOP 拆解。平台将 SOP 中的原始流程语句拆解为“步骤、判断、动作”三类单元。识别、抽取、解析、分类类语句通常对应基础处理能力；判断、校验、匹配、评估类语句通常对应行业判断能力；提交、审批、通知、下单、写入系统类语句通常对应企业流程动作。通过该拆解，平台能够初步识别 Skill 的天然边界，而不是将一整份 SOP 粗糙地打包为单个大 Skill。

第四阶段为 Skill Candidate 生成。系统按照“最小稳定复用单元”原则，为每个候选能力补齐 `name`、`goal`、`trigger`、`inputs`、`outputs`、`steps`、`decision_points`、`ontology_dependencies`、`cli_dependencies`、`human_in_the_loop` 等字段。该阶段的目标不是直接输出最终 Skill，而是形成可分类、可审核、可测试的中间能力单元。

第五阶段为自动判层。平台根据 Skill Candidate 的复用边界、语义依赖、审批链依赖和企业私有依赖程度，将其划分为 L1、L2 或 L3。判层过程中，平台优先使用“跨行业复用、同行业跨企业复用、企业私有绑定”三段式规则，并辅以行业依赖度、企业私有依赖度、审批链依赖度、Ontology 依赖深度等评分指标，降低误分类风险。

第六阶段为依赖补全。平台需要为每个 Skill Candidate 显式补齐三类依赖：其一是 Ontology 依赖，即依赖哪些实体、关系、规则、角色；其二是 Skill 依赖，即某个 L3 是否编排多个 L2 与 L1；其三是 CLI 依赖，即哪些动作需要查询外部系统，哪些动作属于受控写操作。该阶段使 Skill 从静态描述转化为运行时可编排的能力节点。

第七阶段为 Human-in-the-Loop 识别。凡 SOP 中出现审批、确认、复核、特批、补充说明、驳回重提等信号时，系统均应默认标记为 HITL 候选节点，并补充 `actor`、`required_input`、`resume_condition` 等恢复所需信息。该设计确保自动流程与人工决策之间存在明确的 interrupt / resume 机制，而非在运行时隐式中断。

第八阶段为 `SKILL.md` 草稿生成。平台基于前述结构化结果，生成面向人类可编辑的 Skill 草稿，包括适用场景、输入输出、执行步骤、Ontology 依赖、CLI 依赖及 HITL 节点说明。该草稿既是企业能力资产的沉淀格式，也是后续编译为运行时 `SkillDefinition` 的源文件。

第九阶段为人工审核与发布。自动提取结果不可直接进入生产运行。平台应遵循“先审 Ontology、再审边界、再审层级、最后审执行权限”的顺序，由平台团队、行业方案团队和企业管理员共同确认 Skill 的边界、依赖和权限设置。审核通过后，系统方可将 Skill 注册入库并编译为运行时可执行对象。

本规范的核心原则包括：不得将整份 SOP 直接生成单一 L3 Skill；不得绕过 Ontology 抽取直接构建 Skill；不得在 L1 中混入企业私有规则；不得让 L2 强绑定单一企业组织结构；不得在执行型 Skill 中省略 CLI 依赖声明；不得对高风险动作省略 Human-in-the-Loop 节点。通过上述约束，平台能够确保 Skill 资产具备长期可维护、可迁移和可审计的工程属性。

#### 4.7.1 SOP 到 Skill 的标准化流程表

| 阶段 | 目标 | 核心动作 | 输出 |
|------|------|----------|------|
| 1. 文档预处理 | 将原始资料转为可解析文本块 | 清洗、切分、分类 | `document_chunks` |
| 2. Ontology 提取 | 建立业务世界模型 | 抽取实体、角色、关系、状态、规则、事件、决策点 | `ontology_candidates` |
| 3. SOP 拆解 | 找出能力边界 | 拆为步骤、判断、动作 | 结构化流程单元 |
| 4. 生成 Skill Candidate | 形成最小稳定复用单元 | 定义输入、输出、步骤、依赖 | `skill_candidate` |
| 5. 自动判层 | 划分 L1 / L2 / L3 | 按复用边界和依赖程度分类 | `candidate_level` |
| 6. 补全依赖 | 使 Skill 可编排 | 绑定 Ontology / Skill / CLI / HITL 依赖 | `dependencies` |
| 7. 识别 HITL | 标出人工决策节点 | 审批、复核、补充信息、特批识别 | `human_in_loop_points` |
| 8. 生成 `SKILL.md` | 输出可编辑能力资产 | 生成标准技能草稿 | `SKILL.md draft` |
| 9. 审核发布 | 防止边界漂移和越权 | 人工审核、修正、注册 | 已发布 Skill |

#### 4.7.2 禁止事项

| 禁止项 | 原因 |
|--------|------|
| 直接把整份 SOP 生成一个大 Skill | 边界失控，不可复用，不可测试 |
| 不经过 Ontology 抽取直接提 Skill | 缺少稳定语义基础 |
| L1 混入企业私有审批规则 | 破坏分层，难以复用 |
| L2 绑定单一企业组织结构 | 失去行业通用性 |
| 执行型 Skill 不声明 CLI 依赖 | 无法受控执行 |
| 高风险流程不标注 HITL | 存在业务与审计风险 |

## 5. CLI Gateway 调用机制设计

### 5.1 推荐方案：继续自研 CLI Gateway

**核心结论：** CLI Gateway 应继续采用自研方案（架构文档 3.4 节设计），不引入 MCP。

#### 5.1.1 安全能力对比

| 安全能力 | 自研 CLI Gateway | MCP Protocol | 差距评估 |
|----------|-----------------|-------------|----------|
| 动态 Token（5min / 一次性 / 参数绑定） | ✅ 核心设计 | ❌ 无此概念 | **不可弥补** |
| 策略决策点（PDP / PIP） | ✅ 完整实现 | ❌ 无 | **不可弥补** |
| 操作级幂等控制 | ✅ key_fields + TTL | ❌ 需完全自建 | MCP 需大量扩展 |
| 熔断降级 | ✅ Circuit Breaker | ❌ 需自建 | MCP 需大量扩展 |
| 审计日志（不可篡改） | ✅ 追加写入 + 数字签名 | ❌ 需自建 | MCP 需大量扩展 |
| 协议适配（REST / GraphQL / SOAP） | ✅ 插件化适配器 | ⚠️ 部分（以 JSON-RPC 为主） | MCP 覆盖不足 |
| Human-in-the-Loop 集成 | ✅ 审批后重新申请 Token | ❌ 需自建 | MCP 无此流程 |
| 参数篡改防护 | ✅ SHA256(params) 绑定 Token | ❌ 无 | **不可弥补** |

> **MCP 不适用的根本原因**
>
> MCP 设计目标是"让 AI 模型安全地访问外部数据和工具"，适用于开发者工具链场景（如 Cursor 调 GitHub、Claude Code 调 Figma）。它的安全模型基于"用户信任的 MCP Server"。
>
> 本平台的 CLI Gateway 面向企业核心业务系统（ERP / OA / CRM），安全模型基于"零信任 + 最小权限 + 操作级授权 + 全链路审计"。这两种安全模型存在**范式差异**，强行用 MCP 适配会导致在 MCP 之上重建整套安全层，得不偿失。

### 5.2 CLI 命令在编排引擎中的注册方式

CLI 命令以编排引擎原生 Tool 形式注册，但所有调用都必须通过 CLI Gateway 的安全管道：

```python
# 伪代码：CLI 命令注册为编排引擎可调用的 Tool
# 具体实现取决于编排框架选型（LangGraph / ADK / AutoGen / 自研）

class CLITool:
    """封装 CLI 命令为编排引擎可调用的 Tool"""

    def __init__(self, command_def: CLICommandDefinition):
        self.command = command_def

    async def __call__(self, **params):
        # 1. 向 Token 服务申请 Operation Token
        token = await token_service.request_token(
            agent_id=self.agent_id,
            operation=self.command.name,
            params=params
        )

        # 2. 如需人工审批，中断等待（编排引擎的 interrupt 机制）
        if token.requires_approval:
            return InterruptSignal(approval_request=token.approval_id)

        # 3. 通过 CLI Gateway 执行
        result = await cli_gateway.execute(
            command=self.command.name,
            params=params,
            token=token
        )

        return result
```

## 6. Human-in-the-Loop 调用机制

### 6.1 推荐方案：编排引擎原生 interrupt / resume

主流编排框架（**OpenClaw** 的 Session/Checkpoint 机制、LangGraph 的 `interrupt_before` / `interrupt_after`、ADK 的 Action Confirmation、AutoGen 的 HumanInputMode）均原生支持在任务检查点暂停执行，等待外部事件后恢复。本平台采用 **OpenClaw** 作为编排引擎，利用其内置的 Session Store 和 Checkpoint 机制，与企微审批卡片机制对接。

#### 6.1.1 审批流程时序

```
员工 @Agent 发起指令
       │
       ▼
┌─────────────────────┐
│ 编排引擎：任务规划    │
│ 识别需要写入操作      │
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│ CLI Tool：申请 Token  │
│ Token 服务 → PDP 检查 │
│ 触发 Human-in-the-Loop│
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│ 编排引擎: interrupt   │  ←── 执行图暂停，状态持久化到存储
│ 推送企微审批卡片      │
└──────────┬──────────┘
           │
     员工点击【确认执行】
           │
           ▼
┌─────────────────────┐
│ 编排引擎: resume      │  ←── 从存储恢复执行图状态
│ Token 服务签发正式 Token│
│ CLI Gateway 执行操作   │
└──────────┬──────────┘
           │
           ▼
    返回结果到企微
```

### 6.2 超时处理与状态管理

| 超时场景 | 超时时间 | 编排引擎行为 | 后续处理 |
|----------|----------|-------------|----------|
| 普通操作 | 24 小时 | Timer 触发 cancel 事件，清理执行图状态 | 通知发起人，记录审计日志 |
| 紧急操作 | 4 小时 | Timer 触发 escalate 事件，修改审批人节点 | 升级至上级审批人 |
| 财务类操作 | 48 小时 | Timer 触发 cancel 事件 | 自动取消，财务审计日志 |
| 批量操作 | 72 小时 | 分批触发 cancel，逐一清理子图 | 分批通知，逐一记录 |

> **编排框架选型: OpenClaw (已确认)**
>
> 经工程评审 (2026-03-19) 确认，采用 **OpenClaw** 作为编排引擎。OpenClaw 满足以下能力要求：
> 1. **执行图状态持久化** — Session Store 支持 Redis 后端，Transcript 支持 PostgreSQL/S3
> 2. **外部事件恢复** — 支持 checkpoint 恢复长时间运行的任务
> 3. **Timer 机制** — 支持超时处理配置
> 4. **AgentSkills 系统** — 与平台 L1/L2/L3 Skills 体系对接
>
> **安全注意：** 需使用 >= v2026.2.26 版本（修复 ClawJacked 漏洞），并配置 `localhostExempt: false` + `requireAuth: true`

### 7.2 调用链路示例：报销流程

以下展示一个完整的报销任务从企微消息到最终执行的全调用链路：

| 步骤 | 组件 | 调用类型 | 具体行为 |
|------|------|----------|----------|
| 1 | 企微消息网关 | — | 接收 `@财务助理` 消息，转发到编排引擎 |
| 2 | 编排引擎 → L1 意图识别 | 预加载节点 | 识别意图为"报销申请" |
| 3 | 编排引擎 → Ontology | 知识注入 (A) | 加载 context-enrichment Skill，注入成本中心等业务上下文 |
| 4 | 编排引擎 → SkillLoader | 能力执行 (B) | 按需加载 L3 技能 `expense-reimbursement-process` |
| 5 | L3 Tool → Ontology | 知识注入 (A) | 查询费用归属的成本中心 |
| 6 | L3 Tool → CLI Tool | 系统操作 (C) | 调用 `erp.expense.query` 核对费用明细 |
| 7 | CLI Tool → Token 服务 | 系统操作 (C) | 金额 > 1000 元，PDP 判定触发 Human-in-the-Loop |
| 8 | 编排引擎 → interrupt | HITL | 执行图暂停，推送企微审批卡片 |
| 9 | 员工点击【确认执行】 | HITL | resume 执行图，Token 服务签发正式 Operation Token |
| 10 | CLI Gateway → ERP | 系统操作 (C) | 执行 `erp.expense.submit`，记录不可篡改审计日志 |
| 11 | 编排引擎 → 企微消息网关 | — | 将结果以卡片形式推送回企微 |

## 8. MCP 引入路线图（V2.0+）

虽然 V1.0 不引入 MCP，但应为 V2.0 的多渠道扩展预留架构接口。

| 版本 | MCP 应用场景 | 价值 | 优先级 |
|------|-------------|------|--------|
| V2.0 | 飞书/钉钉 IM 平台接入 | 通过 MCP 标准化 IM 消息网关接口 | 高 |
| V2.0 | 第三方 SaaS 工具集成 | 通过 MCP 让 Agent 访问 Notion / Jira 等工具 | 中 |
| V2.5 | 客户自建 MCP Server | 允许客户将自有系统暴露为 MCP Server | 低 |

> **V2.0 MCP 接入的架构预留**
>
> 建议在 CLI Gateway 的插件化适配器架构中预留 MCP Client 适配器插槽。V1.0 阶段仅实现 REST / GraphQL / SOAP 三种适配器；V2.0 新增 MCP Client 适配器，使 Agent 可通过同一 CLI Gateway 安全管道调用 MCP Server。这样 MCP 调用也能享受到动态 Token、PDP 策略决策和审计日志的保护。

## 10. 决策总结

| 决策项 | 结论 | 关键理由 |
|--------|------|----------|
| **Ontology 调用机制** | Graph RAG + Agent Skills 查询策略 | "认知"而非"动作"，适合上下文注入 |
| **L1 通用技能** | 编排引擎原生预加载节点 | 高频调用，P95 < 3s 延迟要求 |
| **L2 行业技能** | Agent Skills 格式定义 → 编译为编排引擎 Tool | 需要版本控制和行业包分发 |
| **L3 私有技能** | Agent Skills 格式（核心资产）→ 编译为编排引擎 Tool | 产品护城河，跨模型可移植，业务可编辑 |
| **CLI 命令执行** | 自研 CLI Gateway + 编排引擎 Tool Call | 安全模型远超 MCP（Token / PDP / 幂等 / 审计） |
| **Human-in-the-Loop** | 编排引擎原生 interrupt / resume | 原生支持，与企微审批卡片天然契合 |
| **MCP 引入时机** | V1.0 不引入，V2.0 用于多 IM 平台扩展 | V1 单渠道无需跨平台工具共享 |
