## 1. 文档目标

本文档目标不是“证明 AI 很强”，而是把输入材料中已经暴露出的真实问题，重构为一套可实施、可验证、可审计的场景化能力设计。

本文档输出内容包括：

- 统一的设计原则与边界
- 面向瓷砖生产企业的 5 个优先场景
- 每个场景的 Ontology 提取结果
- 每个场景的 `L1 / L2 / L3 Skills` 定义
- Agent 平台编排流程
- CLI 调用设计
- Human-in-the-Loop 节点
- 上线前前置条件与验收标准

## 2. 设计原则与边界

### 2.1 从诊断结论倒推能力设计

两份输入文档的共同结论非常明确：

- 当前欧神诺的核心问题首先是数据治理不足，而不是缺少 AI 页面
- 当前很多跨部门协同实际上是“靠人肉补流程缺陷”
- 当前很多场景隐含激励失真、信息隐瞒、系统口径不一致的问题

因此，本设计文档默认以下原则：

- **不把数据未准备好的场景直接设计成全自动执行**
- **不把制度问题伪装成模型问题**
- **不让 Agent 在权责不清的环节越权做决定**
- **不把微信群和人工协调简单替换成“AI 自动化”**

### 2.2 三层 Skills 的严格定义

`L1 Skills`

- 定义：不带企业私有语义的基础原子能力
- 典型职责：意图识别、字段抽取、摘要、表单草稿、澄清追问、结构化输出
- 约束：不承载审批逻辑，不直接调用高风险业务 CLI

`L2 Skills`

- 定义：带行业语义、可在建材/制造行业跨企业复用的业务能力模块
- 典型职责：库存风险判断、窑炉参数异常检测、采购规则预检、经销商补货评估、客户续约评分
- 约束：可以依赖行业 ontology，但不绑定欧神诺的专属制度和组织结构

`L3 Skills`

- 定义：绑定欧神诺企业 ontology、岗位职责、审批链和例外规则的专属流程能力
- 典型职责：欧神诺采购 RFQ 协同流程、欧神诺釉料试烧协同流程、欧神诺经销商补货审批流程
- 约束：允许编排多个 L2 / L1，并与 CLI Gateway、HITL 节点衔接

### 2.3 Agent 平台的边界

Agent 平台负责：

- 加载上下文
- 选择与装配 skill
- 编排任务顺序
- 管理 interrupt / resume
- 记录状态和异常

Agent 平台不负责：

- 修改企业制度
- 越权审批
- 替代质量负责人、财务负责人、销售负责人作最终拍板

### 2.4 CLI 的边界

CLI 只负责受控的系统访问与动作执行。

CLI 必须满足：

- 明确的命令定义和参数 schema
- 只读与写入能力分级
- 动态 token / RBAC / 审计日志
- 幂等键
- 超时和回滚机制

CLI 不负责：

- 解释业务规则
- 决定是否应该执行
- 绕过审批直接修改业务系统

## 3. 场景优先级选择

结合输入文档中出现频率、业务价值、风险等级、可落地性，本文优先设计以下 5 个场景：

1. 采购 RFQ 协同与自动路由
2. 釉料开发与试烧协同
3. 工厂窑炉异常监测与参数建议
4. 经销商补货计划与库存透明化
5. CRM 客户续约与新品推荐

这 5 个场景分别对应输入文档中的核心角色与问题：

- 邓涛：采购协同靠微信群
- 阮娈舒：釉料开发依赖人工试错和供应商反复沟通
- 工厂生产：AI 控制前提不清、操作工信任风险高
- 销售总监：经销商库存、预算和渠道信息缺失
- 客户管理专员 Z：CRM 已见成效，但集成和数据质量仍需补强

## 4. 共用前置条件门槛

以下条件未满足时，相关场景不得进入“自动执行”阶段，只能进入“辅助建议”阶段。

| 门槛项 | 最低要求 | 说明 |
|---|---|---|
| 主数据统一 | 产品、供应商、经销商、客户、批次、订单编码统一 | 无统一编码则不能做跨系统编排 |
| 数据质量 | 关键字段准确率 >= 95% | 包括采购单、库存、传感器、CRM 客户信息 |
| 数据时效 | 关键事件延迟满足场景要求 | 生产场景建议秒级，经营场景建议小时级 |
| 责任边界 | 每个场景的审批人与异常责任人明确 | 无责任边界则不能全自动路由 |
| CLI 接口能力 | 核心系统支持读写接口或可靠适配 | 无接口则只能做建议，不可闭环 |
| 审计要求 | 所有写操作可追溯 | 尤其采购、质量、财务、CRM 更新 |
| HITL 规则 | 高风险决策节点明确 | 没有审批规则不得自动放行 |

## 5. 场景一：采购 RFQ 协同与自动路由

### 5.1 场景来源

对应输入故事：采购中心邓涛。  
输入文档明确指出：当前采购协同依赖微信群、电话、人工时间表，属于典型的流程缺陷由人来补。

### 5.2 场景目标

将“采购需求发起 -> RFQ 分发 -> 预算校验 -> 供应商报价 -> 合同审批 -> 收货/结算衔接”重构为系统驱动流程，使采购协调员从“人肉转发器”转变为“异常监控与流程优化者”。

### 5.3 业务边界

包含：

- 采购需求标准化接收
- 需求部门、供应商、财务、法务的自动路由
- 节点状态可视化
- 超时催办与异常升级

不包含：

- 供应商最终策略谈判
- 供应商价格博弈本身
- 合同条款自动判定的法律责任

### 5.4 Ontology 提取

#### 实体

- 采购需求
- RFQ
- 供应商
- 合同
- 预算
- 收货单
- 结算单
- 审批节点

#### 角色

- 采购专员
- 需求部门发起人
- 财务审核人
- 法务审核人
- 供应商联系人
- 采购经理

#### 关系

- 采购需求关联一个或多个 RFQ
- RFQ 分发给一个或多个供应商
- 合同绑定预算校验结果
- 收货单与采购订单、合同、结算单对应
- 每个流程节点绑定责任角色

#### 状态

- 草稿
- 待需求确认
- 待供应商报价
- 待预算校验
- 待法务审核
- 待采购经理审批
- 已下单
- 待收货
- 待结算
- 异常中断

#### 规则

- 未完成预算校验不得下发正式采购单
- 未完成法务审核不得签署合同
- 供应商超时未报价必须触发催办或备选供应商流程
- 需求信息不完整不得流转到供应商

#### 事件

- 发起采购需求
- 自动生成 RFQ
- 供应商提交报价
- 预算校验完成
- 合同审批完成
- 触发下单

### 5.5 Skills 定义

#### L1

- `purchase-intent-detection`
- `purchase-form-field-extraction`
- `missing-info-clarification`
- `workflow-status-summary`

#### L2

- `rfq-completeness-precheck`
- `supplier-routing-evaluation`
- `budget-compliance-check`
- `procurement-sla-monitor`

#### L3

- `osn-rfq-collaboration-process`

定义：

- 负责欧神诺采购需求的自动路由、状态跟踪、超时升级与异常转人工
- 编排需求确认、供应商报价、预算校验、法务审核、采购经理审批

### 5.6 Agent 平台编排

1. 接收采购需求消息或表单
2. L1 抽取采购品类、数量、交期、需求部门、预算信息
3. 注入 Ontology 中的采购对象模型、审批规则、角色关系
4. L2 做完整性预检和预算校验预检
5. 若信息缺失，进入 HITL 向需求方补充
6. 加载 `osn-rfq-collaboration-process`
7. 自动路由给供应商、财务、法务
8. 实时监控超时、驳回、异常
9. 在关键审批完成后，调用 CLI 创建订单与后续收货/结算链路

### 5.7 CLI 设计

只读 CLI：

- `erp.procurement.request.get`
- `erp.budget.check`
- `supplier.portal.status.get`
- `contract.workflow.status.get`

写入 CLI：

- `erp.rfq.create`
- `erp.rfq.route`
- `contract.workflow.create`
- `erp.po.create`
- `erp.procurement.escalate`

控制要求：

- 所有写入命令需携带 `request_id` 和 `idempotency_key`
- `erp.po.create` 必须以预算校验通过和法务状态通过为前置条件
- 采购经理审批未通过时不得执行写入型下单 CLI

### 5.8 Human-in-the-Loop

- 需求不完整时由需求部门补充
- 预算超阈值时财务人工审批
- 合同高风险条款由法务人工确认
- 供应商长期不响应时采购经理决定是否切换供应商

### 5.9 验收标准

- RFQ 自动路由覆盖率 >= 85%
- 人工电话/微信群协调量下降 >= 70%
- 关键节点状态可视化覆盖率 = 100%
- 超时节点自动提醒成功率 >= 95%

## 6. 场景二：釉料开发与试烧协同

### 6.1 场景来源

对应输入故事：采购中心阮娈舒。  
输入文档指出，该场景不是简单“上数字孪生平台”，而是涉及窑炉传感器、坯体参数同步、供应商激励和试烧反馈闭环。

### 6.2 场景目标

将“坯体变化 -> 釉料方案调整 -> 试烧计划 -> 试烧结果分析 -> 下一轮优化”从高度依赖人工经验、手工沟通和供应商反复扯皮的模式，升级为数据驱动、可追踪、可迭代的研发协同流程。

### 6.3 业务边界

包含：

- 坯体参数、釉料参数和试烧结果的结构化关联
- 试烧任务自动创建与协同
- 候选配方建议与试烧结果闭环

不包含：

- 完全替代研发工程师决定配方
- 在供应商能力不明时自动下结论
- 无质量数据支持下直接自动发配方

### 6.4 Ontology 提取

#### 实体

- 坯体配方
- 釉料配方
- 原材料
- 供应商
- 窑炉参数
- 试烧任务
- 试烧结果
- 缺陷类型

#### 角色

- 釉料工程师
- 坯体工程师
- 供应商技术人员
- 试烧管理员
- 品质工程师
- 采购专员

#### 关系

- 坯体参数影响釉料适配
- 原材料来自指定供应商
- 试烧任务使用特定窑炉参数和配方版本
- 缺陷结果回溯到配方、窑炉、原料批次

#### 状态

- 待评估
- 待试烧
- 试烧中
- 待分析
- 待优化
- 已确认
- 已驳回

#### 规则

- 窑炉关键数据覆盖率不足时不得启用自动配方建议
- 坯体参数变更后必须重新触发适配评估
- 高风险原料替代必须经研发和品质双确认
- 试烧失败必须形成原因归因记录

#### 事件

- 坯体参数变更
- 供应商原料变更
- 发起试烧
- 上传试烧结果
- 生成优化建议

### 6.5 Skills 定义

#### L1

- `formula-change-detection`
- `trial-batch-data-extraction`
- `result-summary-generation`
- `issue-clarification-dialog`

#### L2

- `kiln-parameter-quality-check`
- `glaze-body-compatibility-evaluation`
- `trial-result-defect-classification`
- `supplier-capability-risk-evaluation`

#### L3

- `osn-glaze-development-collaboration-process`

定义：

- 负责欧神诺釉料开发过程中的跨坯体、釉料、供应商、试烧、品质协同
- 不是自动生成最终配方，而是组织评估、试烧、反馈与审批闭环

### 6.6 Agent 平台编排

1. 监听坯体参数变化、供应商原料变化或新品开发需求
2. L1 抽取本次变更的关键字段
3. 注入 Ontology 中的配方对象模型、试烧关系、缺陷语义
4. L2 进行窑炉数据质量检查和适配性预评估
5. 若传感器覆盖、采样延迟、原料信息不满足门槛，则仅输出风险提示，不触发自动建议
6. 若门槛满足，加载 `osn-glaze-development-collaboration-process`
7. 创建试烧任务并指定试烧计划
8. 收集试烧结果并归类缺陷
9. 输出下一轮优化建议或提交研发确认

### 6.7 CLI 设计

只读 CLI：

- `mes.kiln.parameter.get`
- `plm.formula.version.get`
- `qms.trial.result.get`
- `supplier.material.spec.get`

写入 CLI：

- `plm.trial.task.create`
- `plm.formula.review.create`
- `qms.defect.record.create`
- `supplier.change.request.create`

控制要求：

- 若 `kiln_data_quality_score < threshold`，禁止执行自动推荐写入
- 所有试烧任务需绑定 `formula_version_id`、`body_version_id`、`supplier_batch_id`
- 试烧失败结论不得直接回写量产方案，必须经人工确认

### 6.8 Human-in-the-Loop

- 研发工程师确认配方建议是否可试烧
- 品质工程师确认缺陷归因是否成立
- 供应商原料替代方案由采购和研发共同确认

### 6.9 验收标准

- 试烧任务创建时关键信息完整率 >= 98%
- 配方/坯体/窑炉/原料批次关联成功率 = 100%
- 试烧反馈闭环时长下降 >= 40%
- 研发对建议结果采纳率 >= 60%，低于此值则回到模型与规则复核阶段

## 7. 场景三：工厂窑炉异常监测与参数建议

### 7.1 场景来源

对应输入故事：工厂需求故事。  
输入文档明确提醒：该场景不能直接从“传感器多”推导出“可全自动控制”，必须先回答数据质量、控制权、异常回退和操作工信任问题。

### 7.2 场景目标

通过对窑炉实时参数、成型数据、质检结果和历史异常样本的关联分析，提供可解释的异常预警和参数建议，优先从“辅助决策”做起，再评估是否进入部分自动控制。

### 7.3 业务边界

包含：

- 异常识别
- 预警与建议
- 结果反馈闭环

不包含：

- 初期阶段直接自动下发控制命令给 PLC
- 绕过当班操作工与工艺工程师

### 7.4 Ontology 提取

#### 实体

- 窑炉
- 窑段
- 传感器
- 温度曲线
- 气氛参数
- 批次
- 砖坯
- 缺陷类型
- 工单

#### 角色

- 当班操作工
- 工艺工程师
- 设备工程师
- 质量主管

#### 关系

- 传感器属于某窑段
- 批次通过某窑炉烧制
- 缺陷结果对应某批次和工艺参数区间
- 参数建议与工艺规则、历史工单相关联

#### 状态

- 正常运行
- 预警
- 异常确认中
- 参数调整中
- 回退中
- 待复盘

#### 规则

- 传感器异常或丢包时禁止自动控制
- 高风险参数调整必须人工确认
- 参数建议必须附带可解释依据
- 质量结果必须回写用于后验校验

#### 事件

- 参数异常
- 批次偏差
- 触发预警
- 人工确认调整
- 质量复检

### 7.5 Skills 定义

#### L1

- `sensor-stream-anomaly-summary`
- `batch-context-assembly`
- `operator-dialog-support`

#### L2

- `kiln-anomaly-detection`
- `parameter-adjustment-recommendation`
- `sensor-health-check`
- `quality-impact-estimation`

#### L3

- `osn-kiln-anomaly-assist-process`

定义：

- 为欧神诺窑炉运行提供异常识别、建议解释、人工确认、结果复盘的完整协同流程
- 初期定位为“建议型 L3”，不等于“全自动闭环控制”

### 7.6 Agent 平台编排

1. 实时接收窑炉流式数据和批次上下文
2. L2 检查传感器健康度和异常特征
3. 若数据缺失或健康度不足，自动降级为“仅告警，不建议”
4. 若数据健康，生成参数建议及其解释
5. 由 `osn-kiln-anomaly-assist-process` 将建议推送给操作工和工艺工程师
6. 操作工确认后，再调用 CLI 执行受控调整
7. 质量结果回写并评估建议有效性

### 7.7 CLI 设计

只读 CLI：

- `mes.kiln.realtime.get`
- `mes.batch.context.get`
- `qms.batch.quality.get`
- `iot.sensor.health.get`

写入 CLI：

- `mes.kiln.adjustment.request.create`
- `mes.kiln.operator.confirm.record`
- `mes.kiln.rollback.request.create`
- `qms.batch.review.task.create`

控制要求：

- 初期禁止直接提供 `plc.write` 类型命令给 Agent
- 所有调整动作需保留操作者、班次、参数前后值和依据
- 若 15 分钟内质量风险扩大，则自动触发回退建议

### 7.8 Human-in-the-Loop

- 操作工确认是否采用建议
- 工艺工程师审批高风险参数变更
- 质量主管复核异常批次处理结论

### 7.9 验收标准

- 预警命中率达到约定阈值后才允许扩大范围
- 误报率可控并持续下降
- 建议解释被操作工理解和接受的比例 >= 80%
- 所有参数建议执行均可审计回溯

## 8. 场景四：经销商补货计划与库存透明化

### 8.1 场景来源

对应输入故事：销售总监。  
输入文档指出，该场景的核心不是“做个 BI 面板”，而是经销商数据接入不足、库存口径不统一、激励机制导致瞒报。

### 8.2 场景目标

在不回避经销商利益博弈的前提下，建立“经销商库存透明度 + 补货建议 + 预算支持”的协同机制，先实现“辅助决策和异常识别”，再逐步推动自动化预算建议。

### 8.3 业务边界

包含：

- 经销商库存、发货、项目报备、销量的统一视图
- 补货建议和异常识别
- 月度预算建议生成

不包含：

- 直接代替销售总监做区域策略拍板
- 在接入率不足时输出高置信度预测结论

### 8.4 Ontology 提取

#### 实体

- 经销商
- 库存
- 销量
- 发货单
- 项目报备
- 补货建议
- 区域
- 月度预算计划

#### 角色

- 销售总监
- 区域经理
- 经销商负责人
- 商机报备组
- 供应链计划员

#### 关系

- 经销商属于区域
- 库存与发货、销量共同决定补货建议
- 项目报备影响未来需求
- 月度预算绑定经销商维度和区域维度

#### 状态

- 数据待校验
- 可用于预测
- 风险异常
- 待区域确认
- 已形成预算建议

#### 规则

- 未达到最低数据接入率的经销商只可输出参考性建议
- 库存分类口径不一致时不得汇总分析
- 超常变动必须触发人工复核

#### 事件

- 经销商上报库存
- 新项目报备
- 月度计划生成
- 库存异常预警

### 8.5 Skills 定义

#### L1

- `dealer-data-normalization`
- `inventory-summary-generation`
- `missing-data-clarification`

#### L2

- `dealer-stock-health-evaluation`
- `replenishment-recommendation`
- `budget-plan-support`
- `abnormal-reporting-detection`

#### L3

- `osn-dealer-replenishment-planning-process`

定义：

- 负责欧神诺经销商库存透明化、补货建议、预算建议及异常升级流程
- 不是“替代管理判断”，而是“提供可信、可解释、可追责的辅助决策”

### 8.6 Agent 平台编排

1. 接入经销商库存、销量、发货、项目报备数据
2. L1 对库存口径、SKU 映射、区域归属做标准化
3. L2 评估库存健康度和异常报数风险
4. 数据门槛不足时，标记为低可信度并转人工
5. 加载 `osn-dealer-replenishment-planning-process`
6. 输出补货建议、预算建议、风险经销商名单
7. 由区域经理确认后，再触发供应链或销售后续动作

### 8.7 CLI 设计

只读 CLI：

- `crm.dealer.profile.get`
- `wms.dealer.stock.get`
- `erp.shipment.history.get`
- `crm.project.filing.get`

写入 CLI：

- `crm.dealer.plan.comment.create`
- `erp.replenishment.proposal.create`
- `crm.dealer-data-anomaly.case.create`

控制要求：

- 写入预算建议前必须记录数据可信度分数
- 对疑似瞒报数据只能创建异常工单，不能直接生成强制补货单
- 所有建议必须带理由和明细来源

### 8.8 Human-in-the-Loop

- 区域经理确认补货建议是否采纳
- 销售总监确认区域预算方案
- 对高风险异常报数，由经销商运营人工复核

### 8.9 验收标准

- 经销商数据接入率达到阶段目标
- 库存异常识别准确率持续提升
- 区域经理对建议采纳率和修正率有可追踪数据
- 月度预算计划准备周期缩短 >= 50%

## 9. 场景五：CRM 客户续约与新品推荐

### 9.1 场景来源

对应输入故事：客户管理专员 Z。  
该场景是输入文档里相对成熟的案例，但仍存在 CRM 与 ERP/财务同步、数据更新及时性、提醒有效性等风险。

### 9.2 场景目标

把“客户信息标准化 -> 合同到期提醒 -> 跟进任务 -> 新品推荐 -> 复购提升”设计成一个真正闭环的客户经营流程，而不是一个只会提醒却没有后续动作的 CRM 页面。

### 9.3 业务边界

包含：

- 客户画像统一
- 合同到期与复购风险识别
- 跟进任务自动创建
- 新品推荐建议

不包含：

- 直接替销售做成交承诺
- 无客户权限支持下自动发营销信息

### 9.4 Ontology 提取

#### 实体

- 客户
- 联系人
- 合同
- 跟进记录
- 产品偏好
- 复购评分
- 推荐产品

#### 角色

- 客户管理专员
- 销售
- 区域经理
- 财务应收负责人

#### 关系

- 客户拥有联系人和合同
- 合同状态影响续约任务
- 产品偏好与历史采购共同决定推荐产品
- 应收状态影响续约优先级

#### 状态

- 正常经营
- 待续约提醒
- 待跟进
- 待审批报价
- 已续约
- 高流失风险

#### 规则

- 合同到期前 N 天自动进入提醒窗口
- 客户应收异常时不得直接触发续约报价
- 低质量客户资料必须先补齐再进入推荐流程

#### 事件

- 合同即将到期
- 新品上市
- 销售完成跟进
- 生成推荐清单

### 9.5 Skills 定义

#### L1

- `customer-profile-normalization`
- `followup-record-summary`
- `renewal-task-draft`

#### L2

- `contract-renewal-risk-evaluation`
- `product-recommendation-generation`
- `followup-priority-scoring`
- `receivable-risk-check`

#### L3

- `osn-crm-renewal-and-recommendation-process`

定义：

- 负责欧神诺客户续约提醒、新品推荐、任务生成与风险拦截流程
- 重点是形成“提醒 -> 行动 -> 反馈 -> 复盘”的闭环

### 9.6 Agent 平台编排

1. 监听合同到期、新品上市、客户行为变化
2. L1 统一客户资料并汇总最近跟进内容
3. 注入 Ontology 中的客户、合同、应收、产品偏好关系
4. L2 计算续约风险、推荐产品和优先级
5. 若客户资料不完整或应收异常，先转人工治理
6. 加载 `osn-crm-renewal-and-recommendation-process`
7. 自动创建跟进任务并给出推荐理由
8. 销售反馈结果后再更新客户状态

### 9.7 CLI 设计

只读 CLI：

- `crm.customer.profile.get`
- `crm.contract.status.get`
- `erp.receivable.status.get`
- `crm.followup.history.get`
- `product.catalog.recommendable.get`

写入 CLI：

- `crm.followup.task.create`
- `crm.customer.segment.update`
- `crm.recommendation.record.create`

控制要求：

- 应收异常客户只能生成风险提示，不自动生成报价动作
- 所有任务创建必须绑定客户 ID、合同 ID、推荐理由
- 自动更新客户标签需保留变更前后快照

### 9.8 Human-in-the-Loop

- 销售确认推荐是否适配当前客户
- 区域经理审批重大续约报价
- 客户资料缺失时由客户管理专员补齐

### 9.9 验收标准

- 合同到期提醒命中率 >= 95%
- 跟进任务生成与执行闭环率 >= 85%
- 新品推荐被采纳率可衡量并可回溯
- CRM 数据近 90 天更新覆盖率达到目标值

## 10. Agent 平台统一编排模型

为了避免每个场景都走成“各写一套 Agent”，五个场景统一采用如下编排骨架：

1. 事件接入层
   - 接收消息、表单、系统事件、数据变化

2. 上下文装配层
   - 调用 Ontology 查询策略
   - 注入实体、关系、规则、角色、状态

3. L1 基础能力层
   - 做意图识别、字段抽取、澄清、摘要

4. L2 行业能力层
   - 做规则预检、风险识别、匹配、预测、评分

5. L3 场景流程层
   - 负责编排企业专属流程

6. CLI Gateway 执行层
   - 执行只读查询与受控写入

7. Human-in-the-Loop 层
   - 审批、确认、补充信息、异常兜底

8. 反馈闭环层
   - 状态更新
   - 结果回写
   - 指标追踪
   - 案例复盘

## 11. CLI 命名与治理建议

建议欧神诺内部 CLI 不按系统来命名业务意义，而按“领域.动作”命名，系统是实现细节。

推荐命名结构：

`<domain>.<object>.<action>`

示例：

- `procurement.rfq.create`
- `procurement.po.create`
- `formula.trial-task.create`
- `factory.kiln.adjustment.request`
- `dealer.replenishment.proposal.create`
- `crm.followup.task.create`

每个 CLI 定义必须至少包含：

- `command_name`
- `business_owner`
- `input_schema`
- `output_schema`
- `permission_scope`
- `idempotency_key`
- `timeout_ms`
- `side_effect_level`
- `audit_fields`

## 12. 上线顺序建议

### 12.1 第一阶段：只做“建议型”而不是“自动执行型”

优先上线顺序：

1. CRM 客户续约与新品推荐
2. 采购 RFQ 协同与自动路由
3. 经销商补货计划与库存透明化
4. 釉料开发与试烧协同
5. 工厂窑炉异常监测与参数建议

原因：

- CRM 和采购协同相对更适合先做流程透明化和任务自动化
- 经销商场景受制于数据接入率和激励机制，需要先做可信度分层
- 釉料和窑炉场景风险最高，必须晚于数据门槛达标后再推进

### 12.2 第二阶段：从“建议”升级到“受控执行”

只有同时满足以下条件时，相关场景才可从建议型升级到半自动执行型：

- 数据质量稳定达到门槛
- 审批链和异常回退机制明确
- CLI 写入能力成熟
- 人工采纳率和建议命中率达到目标值

## 13. 本设计与原始故事的根本差异

原始故事的问题在于默认：

- 数据已准备好
- 流程会自然改变
- 人会天然配合系统
- AI 可以直接解决制度问题

本文档明确反其道而行之：

- 先定义数据和语义，再定义能力
- 先定义前置门槛，再定义自动化
- 先定义权责和人工节点，再定义 Agent
- 先定义 CLI 边界，再谈闭环执行

因此，这不是“讲得好听”的用户故事设计，而是一份可以进入产品、架构、实施三方共同评审的场景化能力设计底稿。
